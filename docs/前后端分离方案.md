# 前后端分离方案 · Next.js + Rust + PostgreSQL

> 目标：前端保持 Next.js 不动，后端用 Rust，数据库用 PostgreSQL。**前后端分离**，各自独立部署。
> 状态：架构已定，未开工。本文是实施蓝图，配套 `开发文档.md` §14。
> 撰写：2026-10-22（上一版为「SQLite 优先」的过渡稿，本版按终态重写）

---

## 1. 结论先行

| 项 | 结论 |
|---|---|
| 前端 | **Next.js 15 + React 19 原样保留**：SSR、样式、交互、端能力全部不动，只把 `lib/*` 的取数改成 HTTP |
| 后端 | **Rust（axum）** 独占 `/api/v1/**`、会话、鉴权、业务与外部集成，独立进程、独立部署 |
| 数据库 | **PostgreSQL 18**（当前稳定线，18.6；19 于 2026-11-19 GA，暂不追） |
| 分离方式 | **路径分离**：同域名下 `/api/*` 直连 Rust，其余走 Next。不用跨域 + CORS，Cookie 不用改 `SameSite` |
| 迁移方式 | JSON 文件 → PostgreSQL 一次性导入；**老会话与老密码继续有效**，切换当天不掉线 |
| 工期 | 单人 **21–26 人日**（≈5–6 周），7 个阶段 |
| 验收 | `smoke.sh` 164 条断言全绿，Node 版与 Rust 版各跑一遍；再加 `cargo test` 的兼容性 fixture |

一句话：**浏览器看到的还是一个站点，部署上是三个进程（nginx / Next / Rust）+ 一个数据库。**

## 2. 现状盘点

先把要搬的东西量清楚。

| 层 | 规模 | 说明 |
|---|---|---|
| API 路由 | 24 个 `route.ts` | `app/api/v1/**` 23 个 + `/api/health` |
| 领域库 | 26 个模块 / 3388 行 | `users` `session` `forum-store` `sponsor-store` `settings` `oauth` `geetest` `afdian` … |
| 页面数据入口 | Server Components 直连 `lib/*` | **最大的坑**：页面不打自己的 API，而是直接 import 函数 |
| 存储 | `$DATA_DIR/*.json` 6 个文件 | 原子写 + 进程内串行，没有跨进程锁 |
| 前端 | 78 个 tsx / 51 个 ts | 不迁移 |

两条数据通路必须同时改，否则会出现「读走 Node、写走 Rust」的双写风险：

```
① 页面渲染：RSC ──import──▶ lib/*  ──▶ JSON
② 写操作：  浏览器 ──fetch──▶ route.ts ──▶ lib/* ──▶ JSON
```

## 3. 为什么是这个组合（以及被否掉的）

| 选项 | 结论 | 理由 |
|---|---|---|
| **Next 保留 + Rust 后端 + PG** | **采用** | 前端零回归；后端可独立扩缩容；PG 有事务、并发、备份与成熟运维工具 |
| 前端也换成 Rust（Leptos/maud） | 否 | 78 个组件重写、6–10 周、交互回归风险高。详见 §17 |
| 后端 Rust + SQLite | 否 | 只适合单机单写；备份要 `.backup`；跨主机无法共享。既然要多实例与规范运维，直接上 PG |
| 只把存储换成 PG，API 留在 Next | 否 | 没解决"后端语言"的诉求，还多一层进程间调用 |

### 3.1 为什么是 PostgreSQL 18 而不是 19

- 18.6 是当前稳定线（2026-08-13 发布）；19 只有 RC1，GA 定在 **2026-11-19**。
- 新站点没有历史包袱，但也没必要用 RC。**先上 18，等 19 GA 后按常规升级路径（`pg_upgrade` 或 dump/restore）跟。**

### 3.2 「分离」到什么程度

前后端分离有两种含义，别混：

| 形态 | Cookie | CORS | 建议 |
|---|---|---|---|
| **路径分离（推荐）**：`example.com/api/*` → Rust，其余 → Next | 同域，`SameSite=Lax` 不变 | 不需要 | 部署解耦、进程独立，但浏览器视角仍是一个站 |
| 域名分离：`api.example.com` | 必须 `SameSite=None; Secure`，或改 Bearer token | 需要白名单 + `credentials` | 只有在"API 要给第三方/多客户端用"时才需要 |

**选路径分离。** 理由是会话 Cookie 现在是 HttpOnly + `SameSite=Lax`，改成 `None` 会削弱 CSRF 防护；而"独立部署"这件事，靠 nginx 分流就能做到，不需要换域名。

> 若将来真要开放 API 给外部：加一层 `/api/public/*` 走 Bearer token（独立发 key），与站内 Cookie 会话并存，互不影响。

## 4. 目标架构

```
                    ┌──────────────────────────────┐
浏览器 ──TLS──▶ nginx│ /api/*  ──────────────▶ Rust :8080 ──┐
                    │ 其余    ──────────────▶ Next :8900 ──┐ │
                    └──────────────────────────────┘       │ │
                                                   内网取数 │ │
                                              ┌────────────┘ │
                                              ▼              ▼
                                          Rust :8080 ──▶ PostgreSQL :5432
```

- 对外只暴露 nginx；`api` 与 `db` 只在容器网络内。
- Next 的 SSR 走**内网直连** Rust（`API_BASE=http://api:8080`），不绕公网。
- 三个进程都可独立重启、独立升级；会话是无状态签名 Cookie，**不需要 sticky session**。

### 4.1 职责边界

规则一句话：**「谁拥有事实」进 Rust，「事实怎么呈现」留 Next。**

| 进 Rust（含 PG） | 留 Next |
|---|---|
| 用户 / 身份 / 会话 / 密码 | 端能力（runtime / form / isWeChat） |
| 帖子 / 评论 / 点赞 / 公约签署 | `bootstrap` 契约与 ETag |
| 公告 / 轮播 / 站点设置 | 徽章与头衔的**渲染** |
| 赞助者快照 / 爱发电同步 / 站内信聚合 | 相对时间（「3 分钟前」）等派生展示 |
| GeeTest 校验 / OAuth 换 token | `changelog.ts`、空态文案、全部 CSS |
| 徽章**判定**（依赖全站统计） | 页面结构与交互 |

> 推论：Rust **不返回** `time: "3 分钟前"`，只返回 `createdAt` 毫秒；`forum-store.ts` 的 `relTime()` 挪到 Next 侧。
> 这是本方案唯一会改动前端数据形状的点。

## 5. 技术选型

版本为 2026-10 查到的稳定版，实际以 `cargo add` 拉到的为准，全部锁进 `Cargo.lock`。

| 用途 | crate | 版本 | 备注 |
|---|---|---|---|
| HTTP 框架 | `axum` | 0.8 | 与 tower 生态一致 |
| 异步运行时 | `tokio` | 1.54 | multi-thread |
| 数据库 | `sqlx` | 0.8 | `postgres` + `chrono` + `migrate`；编译期 SQL 校验 |
| 连接池 | `sqlx::PgPool` | 随 sqlx | `max_connections=20` 起步，见 §5.2 |
| 中间件 | `tower-http` | 0.7 | trace / compression / timeout / set-header |
| 序列化 | `serde` + `serde_json` | 1 | `rename_all = "camelCase"` |
| 密码 | `scrypt` + `rand` | 0.12 / 0.9 | 参数从哈希串里读，**与 Node 完全一致** |
| 会话签名 | `hmac` + `sha2` + `base64` | 0.12 / 0.10 / 0.22 | HMAC-SHA256 + base64url 无填充 |
| 恒定时间比较 | `subtle` | 2 | `ct_eq`，不要 `==` |
| 爱发电签名 | `md-5` | 0.10 | 对方只支持 md5 |
| 出站 HTTP | `reqwest` | 0.13 | `rustls-tls`，不用 OpenSSL |
| 时间 | `chrono` | 0.4 | DB 用 `timestamptz`，API 出口转毫秒 |
| 日志 | `tracing` + `tracing-subscriber` | 0.1 / 0.3 | `RUST_LOG=info,arena_api=debug` |
| 错误 | `thiserror` | 2 | 领域错误；`anyhow` 只在 main/脚本 |
| 配置 | `dotenvy` + 手写 `Config` | 0.15 | 变量名与现有 `.env` 对齐 |

不用 ORM（Diesel/SeaORM）：表少、查询简单，`sqlx` 直写 SQL 更透明；也不引 Redis——会话是无状态签名，站内信是实时聚合，用不上。

### 5.2 连接池与并发

| 参数 | 建议 | 说明 |
|---|---|---|
| PG `max_connections` | 100（默认） | 单机够用 |
| api 池 `max_connections` | 20 | 公式：`(核数 × 2) + 有效磁盘并发`，别把 PG 占满 |
| `acquire_timeout` | 5s | 池满时快速失败，别让用户干等 |
| `idle_timeout` / `max_lifetime` | 10min / 30min | 防止反代/防火墙掐掉空闲连接后拿到死连接 |
| 多 api 实例 | 池上限 × 实例数 < PG 上限 | 3 个实例 × 20 = 60，留 40 给运维与迁移 |
| PgBouncer | 暂不需要 | 到 5+ 实例或连接数吃紧再加（transaction 模式） |

**必须用事务的地方**（现在靠 `serialize()` 串行队列顶着）：

1. 首个用户成为 admin：`pg_advisory_xact_lock` + 事务内 `SELECT count(*)`，并发只有一个拿到 admin；
2. 后台三条防锁死规则：改角色/封禁/删除必须在同一事务里复核「至少剩一个可用管理员」；
3. 点赞：`INSERT ... ON CONFLICT DO NOTHING` 天然幂等；
4. JSON 导入：整个导入一个事务，失败整体回滚。

### 5.3 前端语言：保持 TypeScript

**分离之后，前后端唯一的耦合是「HTTP + JSON」，跟语言无关。** 换前端语言对适配 Rust 后端没有任何加成，
只会把 78 个 tsx 的存量资产清零（代价见 §17）。所以前端语言**不变**：TypeScript + React 19 + Next.js 15。

真正要解决的是「契约漂移」，用代码生成，而不是靠人手抄：

| 方案 | 做法 | 取舍 |
|---|---|---|
| **OpenAPI 优先（推荐）** | Rust 侧用 `utoipa` 给 handler 与 struct 打标，构建时输出 `openapi.json`；前端用 `openapi-typescript` 生成 `web/src/lib/api-types.ts` | 一份 spec 同时能做文档、mock、第三方接入；多一个构建步骤 |
| `ts-rs` 直出 | Rust struct 上 `#[derive(TS)]`，直接生成 `.d.ts` | 更轻，但只覆盖数据结构，不覆盖路径、方法、状态码 |
| 手写 interface | 现在 `lib/*` 的做法 | 一定会漂移，只适合原型阶段 |

三条约束：

1. 生成的 `api-types.ts` **提交进仓库**，CI 里重新生成一次并 `git diff --exit-code`，有 diff 就说明契约改了没同步；
2. 前端只在 `lib/api-client.ts` 里引用生成类型，页面不直接依赖 —— 换生成器时只改一处；
3. 错误码用 Rust `enum` + `#[serde(rename_all = "snake_case")]` 导出，TS 侧是字面量联合类型，
   `switch` 时能做穷尽检查；中文 `message` 仍由后端给，前端不翻译。

> 如果目标其实是「全栈只用一种语言」，那答案就不是「换个前端语言去适配」，而是把前端也换成 Rust（Leptos）。
> 那是另一个目标（团队心智统一），不是适配成本，取舍与代价见 §17。

## 6. 数据模型（PostgreSQL 18）

### 6.1 设计原则

| 原则 | 做法 |
|---|---|
| 主键不换 | 沿用现 id（`u` + base36 时间戳 + 4 位随机），`text` 主键。**不换成 uuid**，否则老链接、老 Cookie 全废 |
| 时间统一 | DB 用 `timestamptz`（带时区），**API 出口转毫秒整数**，契约不变 |
| 大小写唯一 | 用 `lower()` 唯一索引，不装 `citext` 扩展（少一个依赖） |
| 金额 | `numeric(12,2)`，不用 `float` |
| 列表型字段 | `jsonb`（`tags` / `badges` / `clauses`），体量小，不值得单表 |
| 配置 | `settings(key text primary key, value jsonb)`，**只存被后台改过的键**，删行即回落环境变量 |

### 6.2 DDL

```sql
-- 迁移工具：sqlx migrate；文件名 0001_init.sql，按序号执行，只增不改

CREATE TABLE users (
  id            text PRIMARY KEY,
  username      text NOT NULL,
  nickname      text NOT NULL,
  password_hash text NOT NULL DEFAULT '',        -- scrypt$N$r$p$salt$hash；纯第三方账号为空串
  email         text,
  role          text NOT NULL CHECK (role IN ('admin','member')),
  created_at    timestamptz NOT NULL DEFAULT now(),
  last_login_at timestamptz,
  notif_read_at timestamptz,
  banned        boolean NOT NULL DEFAULT false,
  title         text,
  badges        jsonb NOT NULL DEFAULT '[]'::jsonb
);
CREATE UNIQUE INDEX users_username_lower ON users (lower(username));
CREATE UNIQUE INDEX users_email_lower    ON users (lower(email)) WHERE email IS NOT NULL;
CREATE INDEX users_created ON users (created_at DESC);

CREATE TABLE identities (
  provider  text NOT NULL CHECK (provider IN ('github','cnkd')),
  sub       text NOT NULL,                       -- 平台唯一 id，不是昵称
  user_id   text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  login     text NOT NULL,
  avatar    text,
  PRIMARY KEY (provider, sub)
);
CREATE INDEX identities_user ON identities (user_id);

CREATE TABLE posts (
  id         text PRIMARY KEY,
  title      text,
  body       text NOT NULL,
  guild      text NOT NULL DEFAULT '',
  tags       jsonb NOT NULL DEFAULT '[]'::jsonb,
  author_id  text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX posts_created ON posts (created_at DESC, id DESC);

CREATE TABLE comments (
  id         text PRIMARY KEY,
  post_id    text NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  author_id  text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  body       text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX comments_post ON comments (post_id, created_at);

CREATE TABLE likes (
  post_id text NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  user_id text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  at      timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (post_id, user_id)                -- 幂等：ON CONFLICT DO NOTHING
);

CREATE TABLE agreements (
  id         text PRIMARY KEY,
  title      text NOT NULL,
  short      text NOT NULL,
  version    text NOT NULL,
  scope      text NOT NULL DEFAULT '',
  summary    text NOT NULL DEFAULT '',
  gate       text NOT NULL DEFAULT '',
  clauses    jsonb NOT NULL DEFAULT '[]'::jsonb,
  active     boolean NOT NULL DEFAULT true,
  builtin    boolean NOT NULL DEFAULT false,    -- 内置两份，禁止停用/删除
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE signatures (                       -- 签署从 Cookie 升级成事实
  agreement_id text NOT NULL REFERENCES agreements(id) ON DELETE CASCADE,
  user_id      text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  version      text NOT NULL,
  signed_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (agreement_id, user_id)
);

CREATE TABLE announcements (
  id text PRIMARY KEY, title text NOT NULL, body text NOT NULL,
  kind text NOT NULL, pinned boolean NOT NULL DEFAULT false,
  published boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX announcements_list ON announcements (published, pinned DESC, created_at DESC);

CREATE TABLE slides (
  id text PRIMARY KEY, kicker text NOT NULL DEFAULT '', title text NOT NULL DEFAULT '',
  "desc" text NOT NULL DEFAULT '', cta text NOT NULL DEFAULT '', href text NOT NULL DEFAULT '',
  bg_color text NOT NULL DEFAULT '', bg_image text NOT NULL DEFAULT '',
  text_tone text NOT NULL DEFAULT 'light', active boolean NOT NULL DEFAULT true,
  ord integer NOT NULL DEFAULT 0                -- order 是保留字，列名用 ord，序列化仍叫 order
);

CREATE TABLE sponsors (
  id text PRIMARY KEY, name text NOT NULL, avatar text,
  amount numeric(12,2) NOT NULL DEFAULT 0,
  plan_title text, first_at timestamptz, last_pay_at timestamptz,
  source text NOT NULL CHECK (source IN ('afdian','manual')),
  hidden boolean NOT NULL DEFAULT false
);

CREATE TABLE settings (key text PRIMARY KEY, value jsonb NOT NULL);

CREATE TABLE meta (key text PRIMARY KEY, value jsonb NOT NULL);  -- syncedAt / schema_version

-- 中文站点的搜索：PG 自带 parser 不切中文，别用 tsvector，用 pg_trgm 的子串索引
-- pg_trgm 是 trusted extension（PG13+），库 owner 即可创建，不需要超级用户
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX posts_body_trgm   ON posts   USING gin (body gin_trgm_ops);
CREATE INDEX posts_title_trgm  ON posts   USING gin (title gin_trgm_ops);
```

### 6.3 JSON → PostgreSQL 的类型映射

| 现状（JSON） | PG | 注意 |
|---|---|---|
| `createdAt: 1792587679201`（毫秒 int） | `timestamptz` | 导入用 `to_timestamp($1 / 1000.0)`；导出时 `extract(epoch)*1000` 取整 |
| `banned?: boolean` | `boolean NOT NULL DEFAULT false` | `undefined` → `false`，别留 NULL |
| `badges?: string[]` / `tags: string[]` | `jsonb '[]'` | 用 `to_jsonb($1::text[])` |
| `amount: number`（REAL） | `numeric(12,2)` | 读出转 f64 再进 JSON，避免出现 `50.000000001` |
| `identities[]` 内嵌在用户里 | 独立表 | 按 `(provider, sub)` 建，冲突则跳过并记日志 |
| 公约签署在 Cookie `ag_trust` | `signatures` 表 | 老 Cookie 保留一个版本周期做兜底（见 §7.1） |
| `slides.order` | `ord` | SQL 保留字，序列化仍输出 `order` |
| 帖子 `likes` 计数 | 由 `likes` 表 `count(*)` | 现在 JSON 存的是"额外点赞数"，导入时要与基线合并 |

### 6.4 一次性导入工具

`arena-api migrate --from $DATA_DIR [--dry-run]`

1. 读 6 个 JSON，先在内存里做完整性检查（id 唯一、外键可解析、时间戳合法）；
2. `--dry-run` 打印每张表将写入的行数、被跳过的孤儿数据、金额合计；
3. 实际导入：**单个事务**，按 `users → identities → posts → comments → likes → agreements → signatures → announcements → slides → sponsors → settings` 顺序插入；
4. 幂等：全部 `ON CONFLICT (id) DO UPDATE`（`identities` 按 `(provider, sub)`），可重复跑；
5. 结束后对比：行数、`sum(amount)`、抽样 3 条帖子的评论数，与 JSON 侧一致才提交。

## 7. 兼容性红线（决定能不能"平滑切换"）

| # | 契约 | 现在的精确格式 | Rust 必须怎么做 |
|---|---|---|---|
| 1 | 会话 Cookie | `ba_session = <userId>.<exp 秒>.<base64url(HMAC-SHA256(secret, "<userId>.<exp>"))>` | 签名入参是拼接后的**文本**；base64 用 URL_SAFE **无填充** |
| 2 | 会话密钥 | `SESSION_SECRET` 优先；否则 `$DATA_DIR/.session-secret` | **复用同一个文件**，Rust 不能另生成。这是最容易踩的坑 |
| 3 | 密码哈希 | `scrypt$16384$8$1$<base64 盐 16B>$<base64 key 64B>` | salt/key 用**标准 base64**（不是 URL-safe）；N/r/p 从串里解析 |
| 4 | Cookie 属性 | HttpOnly / SameSite=Lax / Path=/ / 7 天 / `Secure` 仅当 `x-forwarded-proto: https` | 逐项照抄；因为走路径分离，`SameSite` 不用改 |
| 5 | 错误响应 | `{ "error": "username_taken", "message": "该用户名已被占用" }` | 错误码与中文文案逐条对齐，统一放 `errors.rs` |
| 6 | 时间戳 | 全部毫秒（`Date.now()`） | DB 存 `timestamptz`，**API 出口**统一 `.timestamp_millis()`；禁止在某个接口漏出 RFC3339 |
| 7 | JSON 键名与缺省 | camelCase；`undefined` 的键不出现，`null` 才输出 null | `rename_all = "camelCase"` + `skip_serializing_if = "Option::is_none"` |

### 7.1 公约签署的过渡

现在签署状态在 Cookie（`ag_trust` = `版本.时间戳`）。迁到 `signatures` 表后：

- 优先读表；
- 表里没有时，回退读旧 Cookie，**并顺手补写一行**（写一次即可，下次就走表）；
- 一个版本周期（约 2 个月）后删除回退分支。

这样老用户不会因为"没签过"被拦在发帖之外。

### 7.2 必须写的兼容性单测

把现在 Node 生成的三个产物写死成 Rust 测试 fixture：

1. 一个真实 `passwordHash`（明文已知）；
2. 一个真实 `ba_session` token；
3. 一段真实 `users.json`。

`cargo test --test compat` 断言能验通过。**不过就不许发版。**

**scrypt 性能陷阱**：N=16384 单次 50–80ms 纯 CPU，**必须** `tokio::task::spawn_blocking`，否则并发登录把 runtime 线程占满，表现为「登录一多，全站卡住」。

```rust
use base64::engine::general_purpose::STANDARD as B64;
use base64::Engine;
use subtle::ConstantTimeEq;

fn verify_password(password: &str, stored: &str) -> bool {
    let parts: Vec<&str> = stored.split('$').collect();
    if parts.len() != 6 || parts[0] != "scrypt" { return false }

    let (Ok(n), Ok(r), Ok(p)) = (
        parts[1].parse::<u64>(), parts[2].parse::<u32>(), parts[3].parse::<u32>(),
    ) else { return false };

    let (Ok(salt), Ok(expected)) = (B64.decode(parts[4]), B64.decode(parts[5])) else {
        return false;
    };
    if expected.is_empty() { return false }

    let log_n = n.trailing_zeros() as u8;              // 16384 → 14
    let Ok(params) = scrypt::Params::new(log_n, r, p, expected.len()) else {
        return false;
    };

    let mut key = vec![0u8; expected.len()];
    if scrypt::scrypt(password.as_bytes(), &salt, &params, &mut key).is_err() {
        return false;
    }
    key.ct_eq(&expected).into()
}
```

会话验签同理：`hmac::Hmac<Sha256>` 对 `format!("{userId}.{exp}")` 求 MAC，`BASE64_URL_SAFE_NO_PAD.encode` 后 `ct_eq`。

## 11. 部署变更

```yaml
services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_DB: arena
      POSTGRES_USER: arena
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?required}
    volumes: [ "pgdata:/var/lib/postgresql/data" ]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U arena -d arena"]
      interval: 10s
      retries: 5
    # 不发布端口：只在容器网络内可达
    security_opt: [ no-new-privileges:true ]
    shm_size: 256mb

  api:
    build: ./server
    environment:
      DATABASE_URL: postgres://arena:${POSTGRES_PASSWORD}@db:5432/arena
      PORT: 8080
      SESSION_SECRET: ${SESSION_SECRET:-}
      ADMIN_TOKEN: ${ADMIN_TOKEN:-}
      PUBLIC_BASE_URL: ${PUBLIC_BASE_URL:-}
      RUST_LOG: info,arena_api=info
    depends_on: { db: { condition: service_healthy } }
    volumes: [ "session-secret:/data" ]     # 只放 .session-secret
    healthcheck:
      test: ["CMD", "/app/arena-api", "healthcheck"]   # 自带子命令，镜像里不用装 curl
    cap_drop: [ ALL ]

  web:
    build: ./web
    environment: [ API_BASE=http://api:8080, PORT=8900 ]
    depends_on: { api: { condition: service_healthy } }

volumes:
  pgdata: {}
  session-secret: {}
```

要点：

- **迁移用编译期内嵌**：`sqlx::migrate!("./migrations")` + 启动时 `run()`。sqlx 在 PG 上会取 advisory lock，多副本同时启动也只会跑一次；迁移失败**直接退出**，不要带着旧 schema 提供服务。
  （若坚持用外部 `sqlx-cli`，就得自己保证只让一个 job 跑。）
- **healthcheck 别依赖 curl**：`debian:bookworm-slim` 默认没有 curl/wget。要么在镜像里装 curl，要么给二进制加个 `arena-api healthcheck` 子命令，compose 里直接调它。
- **备份**：`pg_dump -Fc -U arena arena > arena-$(date +%F).dump`，每日定时；恢复 `pg_restore -d arena`。演练一次并写进运维手册。
- **升级 PG**：小版本换镜像即可；大版本按 `pg_upgrade` 或 dump/restore，19 GA 后再评估。
- **不再需要 `DATA_DIR/*.json`**：卷上只留 `.session-secret`；旧 JSON 归档为只读留证。
- **多实例**：`api` 与 `web` 都可横向扩（会话无状态、无本地写盘），nginx 上轮询即可，不需要 sticky。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 会话/密码不兼容，切换即全员登出 | 高 | §7.2 的 fixture 先写先绿；`.session-secret` 复用 |
| `spawn_blocking` 漏用，登录打满 runtime | 高 | 压测 20 并发登录；code review 检查每个 scrypt 调用点 |
| JSON → PG 类型漂移（时间/金额/布尔） | 中 | 导入器先 `--dry-run`，再对比行数与 `sum(amount)`；`amount` 用 `numeric` |
| 中文错误文案漂移 | 中 | `errors.rs` 单一出口 + 与 TS 码表逐条 diff |
| 连接池占满 / 迁移并发执行 | 中 | 池上限 20、`acquire_timeout=5s`；迁移加 advisory lock |
| 迁移脚本改历史（改 `0001` 而不是新增） | 高 | 只允许新增序号文件；CI 校验 checksum |
| 备份没落地，出事无法恢复 | 高 | 每日 `pg_dump` + 每周恢复演练；文档写清命令 |
| 切换后必须回滚 | 中 | 切换前 `migrate export` 反向导出 JSON；48 小时内保留旧镜像（§13） |
| 团队不熟 Rust，迭代变慢 | 中 | 前端不受影响；后端只改 `server/`，边界清晰 |

## 13. 回滚

1. **切换前**：`arena-api migrate export --out /backup/snapshot-<ts>.json`（格式与现 `*.json` 完全一致）。
2. 切换后 48 小时内出现阻断问题：停 `api` → 起旧版 `web` 镜像（tag 保留）→ 把 snapshot 放回 `$DATA_DIR` → nginx 撤掉 `/api/` 分流。
3. 因为会话密钥与密码格式一致，**回滚后用户仍然不掉线**。
4. 48 小时确认稳定，再删旧镜像与 Next 侧死代码；PG 数据保留一个月再清。

## 14. 明确不做

- 不重写前端、不换 React、不引入第二个前端框架。
- 不改 URL、状态码、Cookie 名——客户端与反代配置零改动。
- 不做跨域 + CORS + `SameSite=None`（见 §3.2）；将来要开放 API 再单开 `/api/public/*`。
- 不做双写灰度：双写制造两个真源，风险远大于收益。
- 不引入 Redis / 消息队列 / k8s：当前体量用不上，会话无状态也不需要集中存储。
- 不顺手做公会/战队/约战——那是产品功能，另立需求。

## 15. 已定与待定

**已定**：前端 Next 保留、后端 Rust、数据库 PostgreSQL、路径分离、JSON 一次性导入、不做双写。

**还需你确认的 4 件小事**：

1. **PG 部署形态**：自建容器（本文默认）还是用托管 PG（云厂商 RDS）？托管的备份/升级更省心，但要走公网 TLS。
2. **是否现在就要多实例**：先单实例跑稳，还是直接把 `api` 起 2 副本验证无状态？
3. **搜索**：先用 `pg_trgm` 子串匹配（够用、中文友好），还是要上分词（`zhparser`/`pg_bigm`，多一个扩展与维护成本）？
4. **切换窗口**：约 10 分钟停写可接受吗？若不可接受，需要额外设计"双读单写"过渡，成本 +2–3 人日。

## 16. 什么时候**不该**做这个迁移

如果动机只是「Rust 更快」——这个站点当前的瓶颈不在 Node，而在 JSON 全量读写与单实例锁。这两点**换 PG 就解决了**，Rust 带来的吞吐提升对一个玩家社区站几乎没有感知。

值得做的理由应该是：想要独立的、可横向扩容的后端；想用 PG 的备份/事务/运维工具；团队要长期用 Rust 维护服务端；或要把后端能力复用到非 Web 端。若这些都不成立，只做「JSON → PG」这一半，投入产出可能更高。

## 17. 附：如果前端也 Rust 化，UI 会受什么影响

结论：**「看起来」几乎能一样，「摸起来」很难一样。**

| 层 | 会不会变 | 原因 |
|---|---|---|
| 视觉样式（颜色、间距、断点、明暗主题） | **不变** | `globals.css` 是纯 CSS 资产，与框架无关 |
| DOM 结构与文案 | 需手抄，可对齐 | 78 个 tsx 的 JSX 要改写，没有自动转换器 |
| 交互与状态 | **会变，主要风险** | 框架行为，不是 CSS 能兜住的 |

实测交互密度：78 个 tsx / 28 个 `'use client'`（36%）/ 23 个用 hooks / 14 个用 `useRouter` / 28 个纯服务端页面。**七成是抄 JSX，三成是重写逻辑**，工期与风险都在那三成。

最易走样的 7 处：`geetest.tsx`（命令式第三方 JS 胶水）、`carousel.tsx`（定时 + 悬停暂停）、`notification-bell.tsx`（开合 / 点外部关闭 / Esc）、`loading.tsx` 的流式骨架（易退化成整页空白）、主题 `data-theme` 直出（易闪白）、`auth-forms` / `composer` 的受控校验时序、14 处 `router.refresh()`（易「操作成功但界面没变」）。

三条路线：`axum + maud + htmx`（视觉高 / 交互中高，最接近只换语言）、Leptos（都高，代价是 WASM 体积与水合）、Yew（SSR 弱，易退化成 CSR）。

建议：**本方案落地并稳定 3–6 个月后再考虑**；真要动就逐页替换，并用 1440 / 900 / 390 三个视口的截图基线逐页比对。
