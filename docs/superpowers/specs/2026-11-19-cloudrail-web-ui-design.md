# 云轨社区 Web 全站 UI 改造设计

日期：2026-11-19
状态：待审阅

## 目标

在保留云轨社区现有内容、路由、权限、业务交互和浅色/深色主题的基础上，统一社区前台、管理后台、运营台的视觉语言；只在合适的页面加入用户提供的滚动与组件动效；随后整理前端样式与共享 UI 的结构，降低后续改版和维护成本。此任务不修改线上站点，也不改变 API 或数据库契约。

## 当前基线

- 产品是内容优先的玩家社区。首页由公告、轮播、发帖入口、信息流筛选、帖子卡片和侧栏概览组成；当前轮播含社区管理的真实内容与素材。
- Web 使用 Next.js App Router、React Server Components、手写全局 CSS、自托管 CloudRail Sans；根布局提供主题与全局样式。`(site)`、`(console)`、`(ops)` 是三个平级布局组。
- 前台已有 sticky topbar、移动端底栏/导航抽屉、发帖与若干业务弹窗；多处组件已有 Portal、键盘关闭及移动端 sheet 模式。设计应扩展这些已存在模式，而非并行引入一套通用框架。
- `web/src/app/globals.css` 约 9,400 行，集中令牌、前台、控制台、运营台、主题覆盖和多轮视觉迭代；`mobile.css` 单独覆盖窄屏。选择器顺序影响现有主题和后台，拆分不能靠大规模重排来“清理”。
- 后台保持分组侧栏与窄屏抽屉；运营台保持紧凑横向导航。访问门禁、路由语义、独立导航匹配和操作权限不属于视觉重构。

## 视觉方向

- 品牌方向：内容优先的「云轨」社区，不做与现有产品割裂的宣传型首页。沿用自托管字体和蓝色品牌识别，以蓝/青作为轨道与交互强调，少量暖色作站点/状态提示；保留既有语义状态色与徽章品牌色。
- 以站点、轨迹、信号灯等细节表达“云轨”，不把网格/发光效果铺满页面。帖子正文与管理数据继续使用清晰、稳定、不透背景的表面，交互层次由间距、层级、边界、焦点和有限阴影表达。
- 浅色/深色主题继续共享语义 token；所有新增颜色先进入主题变量，避免在组件中散落裸色。字体、正文可读性、对比度和当前品牌资产优先于外部模板推荐。
- 前台、后台、运营台共用颜色、间距、圆角、状态、按钮、表单、卡片、表格、提示等视觉原语；不同壳层保持不同信息密度和导航形态。仅在确认语义与行为一致时抽象组件，不合并权限敏感页面。

## 动效与组件取舍

### 使用

1. **轮播视差**：仅用于首页轮播主视觉的装饰背景层；层级跟随真实页面滚动按 0.15、0.4、0.7 系数移动，内容与 CTA 正常滚动。保留当前可管理的标题、文案、图片和链接，不硬编码新内容替换用户已有素材。
2. **滚动淡入**：只用于有明确层级的首页/落地式内容区块和少量长页面分组，元素越过视口 85% 触发，0.7 秒 cubic ease-out 完成 28px 上移与淡入；同组一起出现，滚出视口后重置以便再次进入时重播。帖子信息流中的每条卡片不单独交错动画。
3. **吸顶页头**：保留前台现有吸顶顶栏和其现有公告位置；滚动时补足清晰的表面/阴影过渡。避免因为重排全站公告与头栏而改变所有页面的信息顺序。
4. **模态、抽屉、底部面板**：沿用现有 Portal、弹层、移动端 bottom sheet 与导航抽屉实现；统一遮罩、入/退场时长、焦点可见、Esc/遮罩关闭、滚动锁定与减少动态效果处理。正文或表单内容仍由业务页面提供。
5. **轻提示、标签页、徽标、骨架、空态**：优先复用现有控件，统一视觉 token、明确状态与反馈；不为效果规格新增重复控件或假活动数据。

### 不使用

- 不对社区帖子流、长文或后台列表启用强制滚动吸附、滚动劫持或整页横向滚动；自然滚动、可分享 URL 与阅读连续性优先。
- 不用 parallax 或 scroll-reveal 承载关键文字、状态、链接或唯一操作；关键内容始终在静态/减少动态效果下完整呈现。
- 不在后台数据表、审核队列和权限动作上使用装饰性常驻动画或大幅视差。

### 动态效果无障碍

- 全站监听 `prefers-reduced-motion: reduce`：移除非必要位移、视差和重播，只保留最终可读状态；系统已有此类规则的组件要复用并检查冲突。
- 键盘焦点明显，弹窗聚焦与关闭可预测；可点击目标和移动端触控尺寸满足现有布局约束；提示和状态不只依赖颜色或动画传达。
- 观察/动画不引起布局偏移，不因增加动画而提前加载大型动效库或第三方字体。

## 前端结构整理范围

- 视觉改造后，将全局 CSS 按稳定职责拆为基础与主题令牌、前台外壳/内容、共享组件、管理/运营台、兼容性覆盖等明确入口；`mobile.css` 仍是明确的窄屏最后覆盖层，实际拆分单元以审计现有级联顺序后决定。
- 拆分期间完整保留原选择器相对顺序、媒体查询、主题选择器和覆盖规则；不新增 CSS cascade layers，不做类名全局重命名，不在一次改动中重排全部 9,400 行样式。
- 只抽取可证实为纯视觉且至少由两个表面共用的原语；`(console)` 与 `(ops)` 的布局/导航留在各自 shell；如有必要，提取共享小组件但不改变门禁和 props 权限语义。
- 保持 `web/src/app/layout.tsx` 根布局和页面 Server Component 默认结构，不把数据页转成客户端组件；新增滚动交互作为窄小客户端叶子组件。
- 不整理 Rust、数据库、API、构建部署配置和应用客户端目录；不动当前工作区里的 `promo/`、用户数据、依赖目录或密钥。

## 建议实施顺序

1. 建立现有页面/主题/视口基线，并确认本机 Web 与 API/数据库可运行方式。
2. 完成语义 token、基础控件、前台壳层、内容卡片、控制台与运营台的统一视觉细化。
3. 增加受限的首页视差和可复播滚动 reveal，打磨既有 modal/drawer/sheet 过渡与键盘/减少动态体验。
4. 按原级联顺序拆分大 CSS 文件；清理确认为未使用或重复的样式时，限定到此次涉及的 UI，不删除未知历史覆盖。
5. 跑 typecheck、前端构建、已有冒烟/适用测试；在 375px、768px、1024px、1440px 与两种主题检查主要页面。对于有本机运行环境的情况，核对首页、帖子详情、资源、后台概览、运营审核视图。
6. 检查差异，清理本次产生的 Next `.dist` / `.next` 构建缓存和其他明确生成的构建缓存；保留 `node_modules`、数据库和所有用户内容。若跑后端测试且生成 `server/target`，开发结束时一并清理该构建产物。

## 验收标准

- 三个 Web 表面视觉一致且仍有清晰的信息架构；前台帖子内容易读，console/ops 中的数据、筛选、状态和危险操作不被装饰遮挡。
- 浅色/深色主题、移动端抽屉和底栏、现有弹窗与关键路径继续工作；路由、按钮目的、数据来源、权限以及表单行为无非预期变化。
- 新滚动动效按照既定时序/缓动工作，使用真实滚动而不劫持输入，减少动态效果模式下无失真地显示内容。
- CSS 拆分后显式导入序列稳定；所有关键页面的主题、响应式、焦点、叠层与覆盖和拆分前一致或更好。
- 通过适用的类型检查、构建和冒烟检查；失败项如由缺失的 PG/API、外部服务或存量问题导致，明确记录而不将尝试称为通过。
- 最终工作树中没有本次留下的缓存型构建产物；用户数据和用户已有未跟踪内容保留。

## 风险和控制

- **CSS 级联漂移**：大型全局样式多轮追加且高优先级主题覆盖在文件末端；先记录分段边界，严格保持原序，拆分后做前后对照截图并跑响应式/双主题验证。
- **滚动容器差异**：Web 外壳在 `.site-scroll` 中滚动，不能默认把 window 滚动当唯一坐标源；动效须对容器正确订阅并在 unmount 时清理。
- **服务运行依赖**：页面 SSR 需要 Rust API/PG；如果本地服务不能启动，仍可完成静态编译、类型检查和可运行的验证，并记录需要环境支持的视觉核验。
- **范围**：保持 UI 相关、逐步且可审阅；不为“优化结构”迁移业务域或全仓统一命名。
