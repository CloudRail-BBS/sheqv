## 2. 本地运行

```bash
cd web
npm install
npm run dev            # http://localhost:8900（端口写死在 dev 脚本里，改就改 package.json）
```

生产构建（本机有文件删除守卫时，用新的产物目录并提高阈值）：

```bash
CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=5000 \
NEXT_DIST_DIR=.dist npx next build

npm start              # 默认 8900；PORT=9000 npm start 可临时换
npm run start:standalone   # 跑镜像里的 server.js，验证部署形态
```

> 启动走 `scripts/start.mjs` 而不是直接 `next start -p ${PORT:-8900}`：
> npm 在 Windows 上用 cmd.exe 执行脚本，`${VAR:-default}` 不展开，会传字面量给 next。
> 这层包装同时给 `--standalone` 用（跑镜像里的 `server.js`）。
>
> `start.mjs` 会先调 `scripts/load-env.mjs` 读 `.env`：`next dev` / `next start` 自己会读，
> 但 standalone 的 `server.js` 不保证读，不统一就会出现「.env 里配了却没生效」。
> 规则是**已存在的环境变量优先**，所以容器里 `docker compose environment:` 给的
> `SESSION_SECRET` 不会被 `.env` 里的空值盖掉。

> 本机踩坑：产物目录第一次建时会在 `.dist/trace` 报一次 `EPERM`，重试一次即可；重复构建会因批量删除被守卫拦截。
> 日常迭代用 `next dev` 即可，不需要每次构建。

## 3. 一次请求发生了什么

```
浏览器
  │  GET /  (User-Agent / sec-ch-ua-mobile / cookies: theme, __form)
  ▼
middleware.ts
  │  detectRuntime() → { runtime:'web', form:'desktop|mobile', isWeChat }
  │  写响应头 x-runtime / x-form / x-wechat / Vary
  ▼
app/layout.tsx  (server)
  │  getRequestCaps()  ← React cache，每请求只解析一次
  │  getTheme()        ← 读 theme cookie
  │  输出 <html data-theme data-form data-runtime data-wechat>
  ▼
页面 (server component)
  │  const caps = await getRequestCaps()
  │  用 caps.capabilities.* / caps.limits.* 决定渲染
  ▼
客户端组件（'use client'）
     useCap() 只读消费；不解析 UA，不改能力
```

**不要**在客户端重新判断 UA、窗口宽度来改功能 —— 那会绕过 fail-closed 规则。

## 4. 端能力：三个概念

| 概念 | 取值 | 谁决定 | 影响 |
|---|---|---|---|
| `runtime` | web / android / ios | 构建产物 + 服务端 UA | 契约里的"端" |
| `form` | desktop / mobile | UA / CH / dev cookie | **只影响布局**，靠 CSS 断点落地 |
| `isWeChat` | true / false | UA 含 `MicroMessenger` | 唯一的能力修正因子 |

合并顺序：`DEFAULTS[runtime]` → 微信覆盖（**直接改值**）→ 服务端下发（**AND，只能关**）。

### 加一个能力键

1. `lib/capabilities.ts` 的 `Capabilities` 加字段，四张默认表都补上（web / android / ios；微信覆盖里也补）。
2. `contracts/README.md` §4 矩阵补一行；`bootstrap.openapi.yaml` 的 `Capabilities` 补同名属性。
3. 页面上用 `caps.capabilities.xxx` 判断，不要写 `if (form === 'mobile')`。
4. 顺序不能反：**先发客户端，再让服务端下发**，否则老客户端读到 `undefined`。

### 加一个配额

`Limits` 加字段 → 默认值 → `buildCapabilities` 里 `pick()` 取 `min` → 矩阵同步。

## 5. 页面约定

- 两栏骨架：`<div className="cols"><div className="col-main">…</div><aside className="rail">…</aside></div>`。
- 列表为空时也要有卡片边界，不要裸文本。
- 卡片：`card` + `card-pad`；行内小卡用 `rail-card`。
- 数字统一 `font-variant-numeric: tabular-nums`（`.num` / `.mono`）。
- 表格数字列加 `className="num"` 右对齐。
- 破坏性操作（解散、下架、仲裁）一律二次确认弹窗（`.modal-mask` / `.modal`）。
- **弹窗要 Portal 到 body**。页面根节点带 `pageIn` 入场动画，动画期间会形成 stacking context，
  遮罩的 `z-index` 再高也盖不住顶栏（表现为「内容变暗、顶部栏还亮着」）。
  `.content > *` 的动画因此**不要加 `fill-mode: both`**——结束后仍会保留那层 stacking context。

### 5.0 福利中心（`/rewards`）

- 页头：`REWARDS` 小标 + 标题 + 说明；右侧是积分卡（图标 + 数字 + 明细链接），≤700 占整行。
- 页签是胶囊分段（`.rw-tab`），选中在浅色用面板白、深色用 `--panel-3`；
  切换会改写 `?tab=cards|code|lottery`（`history.replaceState`），刷新/分享保持在同一页。
- 礼品卡是「纸质票根」：浅色卡片在深浅主题下都成立，顶部 3px 主题色条 +
  虚线撕口 + 右下角贴纸式「拆」按钮（54px，落在卡内，避免悬出被相邻卡遮住）。
- 领奖弹窗（`.gift-burst`）Portal 到 body、`z-index: 200`，支持 Esc / 点遮罩关闭、
  打开时锁滚动；票根用「已拆」印章，主按钮横向排列，≤560 占满整行。

### 5.2 帖子详情：逐楼（楼主 + #N）

和 Discuz 的帖子页一致：**每一楼都是一张普通帖子卡**，楼主不是特殊的「主题」：

- 顶部 `thread-head` 只放标题、发布时间、回复/点赞/浏览、标签与「回复帖子」。
- 楼主是 **1 楼**：`article.card.post-block#post-1`，横带里带 `楼主` 蓝色胶囊；
  回复从 **2 楼** 起，横带里放灰色 `#N` 楼号，右侧是「回复」按钮。
- 两者结构、留白、字号完全一致（`.pb-head` / `.pb-body` / `.pb-foot`），
  没有「主题正文」这一类单独的样式。
- 锚点 `#replies` 仍指向**第一条回复**，卡片上的回复图标点过去不会跳回楼主。
- 楼号由后端算（`forum::get` 按时间正序 `enumerate + 2`），前端不自己数。

#### 置顶 / 精华 / 二次编辑

- `posts` 新增 `pinned`、`featured`、`edited_at`（迁移 0042）；列表按 `pinned DESC, created_at DESC`
  排序，置顶帖排最前。
- 管理员在帖子右上角切换「置顶 / 精华」→ `PATCH /api/v1/admin/posts/{id}/flags`。
- 作者本人（或有 `audit.review` 权限的人）可二次编辑 → `PATCH /api/v1/posts/{id}`，
  只改标题与正文，状态不变，`edited_at` 落库后在标题下显示「已编辑」。
- 卡片与详情都会显示 `置顶 / 精华` 胶囊，作者名旁带认证标记（`users.verify_kind`）。

#### 人机验证（弹窗式）

- 发帖 `POST /api/v1/posts` 与评论 `POST /api/v1/posts/{id}/comments` 的 body 可带
  `captcha: { lot_number, captcha_output, pass_token, gen_time }`；后端在配了极验时校验，
  缺票返回 400 `captcha_failed`（文案「请先完成人机验证」）。
- 前端提交前若还没有票据，弹 `CaptchaDialog`（`Geetest auto` 自动拉起验证层），
  通过后带着票据自动继续提交，页面上不再单独摆一个验证按钮；登录/注册表单同样改为自动弹出。

#### 点赞：一人一票

- 明细表 `post_likes(post_id, user_id, created_at)`，主键 `(post_id, user_id)`（迁移 0040）。
- `POST /api/v1/posts/{id}/like` **需登录**，语义是**切换**：没赞过就赞，赞过再点取消；
  返回 `{ likes, liked }`，`posts.like_count` 在同一事务里按明细重算，不会漂。
- 列表与详情都会带 `liked`（当前用户是否赞过），前端按它初始化按钮，
  不再出现「刷新后按钮回到未赞、但计数一直涨」。
- 迁移时把老的 `like_count` 归零重算 —— 旧数据是纯计数器，没有明细可依。

### 5.2b 帖子列表：按内容自适应的瀑布流

`components/post-card.tsx` 是一张高度随内容走的卡片（`article.card.feed-card`），
帖子流用 `column-count: 2` 排成瀑布流（≤860px 单列），每张卡自己算高度、不会互相拉平：

- **有图**：顶部整幅封面，比例取原图（`user_media.width/height`，由首页一次性批量查
  `GET /api/v1/media/sizes` 拿到）。竖图最多裁成 5:4、横图最多 1.9:1，
  避免某一张把整列拉得很长；封面走 `?w=640` 兜底 + `srcSet` 七档。
- **没图**：不占封面位，改成「标题 + 四行摘要」的纯文字卡（`.feed-card-text` / `.fc-excerpt`），
  自然比图片卡矮一截 —— 这就是瀑布流高低错落的来源。
- **信息面板**（`.fc-body`）第一行：头像（32px 圆）→ 昵称 → 分类胶囊（第一个标签，圆点 + 文字）
  → 时间靠右；标题最多两行；底部三个计数：点赞（可点）、回复（跳 `#replies`）、浏览。
- 卡片只挂**头衔**（`UserBadge`，无头衔则不占位）；身份组与成就放在悬浮卡里，
  窄卡片不至于被一堆标签挤成两行。
- 置顶标记浮在封面左上角，鼠标悬停封面轻微放大（1.02）。
- 浏览数：`posts.views`（迁移 0039），详情页每次打开 +1（仅 published），列表直接读。

> 瀑布流按列排：第一列排满再排第二列，所以「第 2 条」会出现在「第 1 条」下方而不是右侧。
> 这是 CSS 多列的天然行为，换来的是零 JS、无闪动的真瀑布流。

### 5.2c 外壳宽度

顶栏、主体、页脚共用 `--shell`（当前 **1600px**），页面左右内边距 18px。
改宽度只动 `:root` 里的 `--shell` 一处，三处容器自动跟随；≤860px 收成单列并降到 16px。

### 6.1 徽章（`.badge` / `.ut`）

一套语义配色 + 三种可叠加的特效，样式只改 class 与 `data-*`，不再各页写内联色：

| 类 | 语义 | 典型用法 |
|---|---|---|
| `badge` | 中性 | 计数、分类、游戏版本 |
| `badge-live` / `badge-warn` / `badge-danger` / `badge-ok` | 进行中 / 待处理 / 错误 / 通过 | 状态 |
| `badge-gold` / `badge-violet` | 荣誉 / 开发者 | 置顶、主办、开发者 |
| `badge-outline` / `badge-ghost` / `badge-solid` | 虚线（草稿）/ 最弱（已结束）/ 实心（当前） | 弱化与强调 |
| `badge-lg` | 大号 | 详情页页头 |

特效是**叠加**的，不新增颜色：

- `data-dot`：文字前加同色圆点；`data-dot="pulse"` 缓慢呼吸（「报名中」这类正在收人的状态）。
- `data-shine`：几秒扫一次高光，只给置顶、管理员头衔这类荣誉徽章，避免列表成片闪。
- `data-glow`：hover 透出同色光晕并上抬 1px，点击前先有反馈。
- `prefers-reduced-motion: reduce` 下呼吸与扫光全部关闭。

赛事状态统一由 `components/tournament-status.tsx` 输出（列表/详情/后台共用一份映射）。

- 游戏标记（Minecraft / Rusted Warfare）文字保持中性，只用 6px 色块区分，避免一屏三套彩色语义。
- 主题写在 cookie 里，SSR 直接输出 `<html data-theme>`，首屏不闪。

## 8. 数据层与接 API 的路径

> ⚠️ 前后端分离已立项且**后端已实现**（见 §14）：`server/` 覆盖了身份、内容、公约、站内信、后台与第三方登录。
> 本节 8.1–8.12 描述的是**当前线上仍生效的 Node 实现**：页面在 Server Component 里直接 `import` 领域函数、
> 函数再读写 `$DATA_DIR/*.json`。Phase 5 会把这些函数换成对内网 Rust API 的封装，**函数签名与页面调用点不变**。
> 在切换完成前，加功能仍按本节写，不要提前假设后端是 HTTP。

现在全部来自 `src/lib/data.ts` 的内存 mock。接后端时按这个顺序：

1. `/api/v1/bootstrap` 已经就绪（含 ETag），客户端用它拿能力与配额。
2. 把 `data.ts` 的数组换成 `fetch` + `cache()`，函数签名保持 `async`，页面不需要改结构。
3. 写接口统一带幂等键（`Idempotency-Key`），比赛提交带 `version` 做乐观锁。

### 8.1 公约签署（签名存 cookie）

- 数据与解析：`lib/agreements.ts`（纯数据，客户端可 import）。
- 服务端读签名：`lib/agreement-state.ts` 的 `getSignatures()` / `isTrustSigned()`。
- 写入：`POST /api/v1/agreements/sign`，写 httpOnly cookie `ag_trust` / `ag_community`，值为 `版本.时间戳`。
- 版本即约束：cookie 里的版本与 `AGREEMENTS[x].version` 不一致 → `signed=false, stale=true`，页面提示重新签署。
- 限制放在**服务端渲染分支**里（如比赛详情页的 `!trustSigned`），前端遮罩不算数。
- 新增一份公约：`AGREEMENTS` 加一项 → 页面与 `/me` 自动出现 → 在需要的地方调用对应的 `isXxxSigned()`。

> 换成真实后端时，把 cookie 校验替换成 `GET /api/v1/agreements/signatures`，其余分支不动。

### 8.2 后台新增公约

- 存储：`lib/agreement-store.ts`，内置两份 + `$DATA_DIR/agreements.json`（后台新增）。
- 落盘：`lib/json-store.ts` 统一提供「临时文件 + rename 原子写」与进程内串行队列；并发新增不会互相覆盖，断电不会留半个 JSON。
- 接口：`GET/POST/PATCH/DELETE /api/v1/admin/agreements`，四个方法都先过 `checkAdminRequest()`。
  - POST 入参 `{ title, version, scope, summary, gate, clauses[] }`，校验失败返回 422 带中文原因。
  - 内置 id `trust` / `community` 禁止停用与删除（403）。
- 页面：`/admin/agreements` + `components/agreement-admin.tsx`（客户端表单 + 表格操作，成功后 `router.refresh()`）。
- 生效链路不用改：`/agreements`、`/me`、签署接口都走 `listActive()` / `getAgreement()`，新增即出现。
- 上生产：把 store 换成 DB 即可，函数签名（list / get / create / setActive / remove）保持不变。

### 8.3 文件存储的边界

| 事实 | 后果 |
|---|---|
| 数据在 `$DATA_DIR`，纯 JSON | 备份 = 打包一个目录，迁移 = 拷目录 |
| 写操作串行化**只在单进程内** | 多实例共享同一目录会丢更新 → 只支持单实例 |
| 无数据库、无 Redis | 没有横向扩容能力；要扩容先换 `json-store` |

### 8.4 站点设置（环境变量搬进后台）

有些值只改代码注释不够，运营必须能自己改，所以做成运行时设置。

| 项 | 存哪 | 生效时机 |
|---|---|---|
| 帖子流样式（单列 / 双列卡片）/ 站点名 / 站点标识（文字+图片）/ GeeTest ID+KEY / 爱发电 user_id+token+主页 / **GitHub 与 CNKD 凭据** / 对外地址 / 开放注册 / 首页公告开关 / **页脚（文案、备案号、链接）** / **页面文案（登录、注册、我的未登录）** | `$DATA_DIR/settings.json` | **立即** |
| `DATA_DIR` / `PORT` | 仅环境变量（compose 或命令行） | 重启 |
| `SESSION_SECRET` / `ADMIN_TOKEN` | 仅环境变量 | 重启 |

优先级：`settings.json` > 环境变量 > 代码默认值。`settings.json` **只存被后台改过的键**，
所以"清掉某个键就回落环境变量"，后台每项旁边都有「恢复环境变量」按钮。

`lib/settings.ts` 只暴露 `getSettings()` / `updateSettings()` / `resetSetting()`；
`geetest.ts` 与 `afdian.ts` 都改成 async 从这里取值，不再直接读 `config`。

**为什么不把密钥也放后台**：`SESSION_SECRET` 与 `ADMIN_TOKEN` 一旦落 JSON，
备份或误提交就会泄漏；这两项留在 `.env` 里由运维管理（不配也能跑：会话密钥自动生成，应急口令默认关闭）。
GeeTest KEY 与爱发电 token 无法回避（运营要自己填），后台页面上明确写了"明文存于数据卷"。

### 8.5 账号体系

```
注册 ──► GeeTest 服务端校验 ──► users.json（第一个用户 role=admin）
                                   │
登录 ──► scrypt 校验 ──────────────┴──► 签名 Cookie（ba_session）
                                          │
                                          └─► getCurrentUser() → 页面 / 接口
```

| 关注点 | 实现 | 位置 |
|---|---|---|
| 密码哈希 | scrypt N=16384 r=8 p=1，16 字节随机盐，参数写进哈希串（可平滑提强度） | `lib/users.ts` |
| 会话 | 无状态签名 Cookie：`userId.exp.hmac`，7 天 | `lib/session.ts` |
| 会话密钥 | `SESSION_SECRET`，缺省自动生成 `$DATA_DIR/.session-secret` | `lib/session.ts` |
| 当前用户 | `getCurrentUser()`，每请求一次（React cache） | `lib/current-user.ts` |
| 首个管理员 | `createUser()` 在同一串行区间内判断 `users.length === 0`，并发也只有一个 admin | `lib/users.ts` |
| 人机验证 | 客户端拿票据 → 服务端算 `sign_token` 换结论 | `server/src/captcha.rs` + `components/geetest.tsx` |

**几个不能改错的点：**

1. **作者只能来自会话**。`POST /api/v1/posts` 忽略客户端传的 `author`，用 `user.nickname` —— 否则谁都能冒充别人发帖。
2. **人机验证必须服务端校验**。前端的 `onSuccess` 只代表"人完成了交互"，票据仍要拿去 `gcaptcha4/validate` 换结论。
   `geetestId` 只在 **id + key 都配好**时才进公开设置；`geetestKey` 永不下发。前端只认 `geetestId`
   决定是否渲染组件 —— 反过来用 key 判断会让普通访客永远拿不到 id，组件不显示、提交却要求验证。
3. **没有默认管理员**。不要为了"方便"加一个内置账号；首次部署引导到 `/register` 即可。
4. **`ADMIN_TOKEN` 是应急通道**，只在显式配置时生效，不参与日常登录。

> **控制台里的 `gcaptcha4.css:1:…` 警告不是本站故障。**
> 那是 GeeTest 官方样式表里给旧 IE 写的兼容写法（`\9`、`*width`、`filter:alpha`、
> `-o-min-device-pixel-ratio`、`-ms-clear` 等），Firefox 会逐条报告「解析…的值时出错」
> 并丢弃该声明。它们只影响这些本就只给 IE 的规则，不影响组件渲染与校验；
> 资源在 GeeTest 的 CDN 上，不在不改动第三方资源的前提下去掉。
> 判断验证是否正常，看 `gcaptcha4/validate` 的请求与后端日志里的 `reason` 即可。

> **bind 模式必须用 `showCaptcha()`，`appendTo()` 无效。**
> 官方文档写明：`product: 'bind'` 时 `appendTo` 调用会被忽略，只有 `showCaptcha()` 才能
> 拉起验证层，而且必须等 `onReady` 之后调用。`components/geetest.tsx` 因此自己画一个
> 「点击完成人机验证」按钮，点击时调 `showCaptcha()`，`onSuccess` 里取 `getValidate()` 票据。
> 早期写成 `bind + appendTo`，现象是 gt4.js / gcaptcha4.css 都加载成功、容器里却始终空白，
> 提交只能报「人机验证未通过」。

### 8.7 公告与轮播

两者都是"后台改、前台立刻变"的内容，不再硬编码在代码里。

```
公告：$DATA_DIR/announcements.json   → /announcements、/announcements/[id]、首页右栏
轮播：$DATA_DIR/slides.json         → 首页 <Carousel slides={...} />
```

- **公告**：`kind` 只有规则 / 版本 / 活动 / 系统；`pinned` 置顶；`published=false` 是草稿，
  前台列表与详情都看不到（详情页 `notFound()`）。
- **全站公告条**：`(site)/layout.tsx` 取最新 3 条已发布公告，`AnnouncementBar` 在顶栏下方
  渲染最新一条（分类胶囊 + 标题 + 全部公告 + 关闭）。关掉的状态按公告 id 存
  `localStorage['crbbs-ann-dismissed']`（最多 20 条），**新公告发布后会自动重新出现**；
  公告页本身不再重复挂这条。所有页面共用同一份布局，所以等于全站常驻提醒。
- **轮播**：每张可设 `bgColor`（预设色板 + 自定义 hex）或 `bgImage`（URL，优先），
  另有 `textTone` 控制文字明暗。`lib/slide-store.ts` 的 `safeHref()` / `safeColor()`
  会挡掉 `javascript:` 之类的注入；`slides.json` 不存在时用内置的三张引导，一旦后台保存过就以文件为准
  （**删光也能生效**，不会被默认值顶回来）。
- 全部轮播停用后，首页直接不渲染这一块，不留空位。

### 8.7b 审核进度（帖子与资源）

帖子和资源共用一套「提交 → 审核 → 发布」的展示：

- 状态：`pending`（待审）/ `published`（已发布）/ `rejected`（驳回）/ `hidden`（下架）。
- 数据：`GET /api/v1/me/submissions` 一次返回自己的帖子与资源（含待审、驳回），
  带 `rejectReason`、`createdAt`、`reviewedAt` 与 `href`；`pendingCount` 给「几条在排队」。
- 展示：`components/audit-progress.tsx`
  - 详情页用完整版：三步时间线 + 状态徽章 + 驳回原因；
  - 列表（我的页）用 `compact`：三条小格 + 状态，不占纵向空间。
- 资源从 0036 起也走审核：`resources.status` 增加 `pending/rejected`，
  `reject_reason` / `reviewed_at` 与帖子同名同义；发布时按 `postAuditMode` 决定直接上线还是进待审。
- 后台 `/admin/audit` 分「帖子 / 资源」两个页签，资源可查看 AI 判定、通过或驳回（驳回必须填原因）。
- 审核结果都会发站内信（`kind=resource` / 帖子沿用人工审核不发）。

### 8.8 站内信

```
评论 ──按 notif_read_at 水位聚合──┐
                                  ├─► getNotifications(user) ──► 顶栏面板 + /notifications
业务事件 ──notifications 表──────┘
```

两类来源合并成一条时间线（迁移 0030）：

- **互动**：别人在我帖子下的评论，按 `users.notif_read_at` 水位算未读，不落行。
- **业务事件**：`notifications` 表逐条记录，`read_at` 标已读。`notifications::push()` 是唯一入口，
  目前接入：
  - 礼品卡到账（后台发卡 `/admin/rewards`）与抽奖中奖 → `/rewards`
  - 头衔申请通过 / 未通过 → `/me`
  - 赛事报名通过 / 未通过 → `/tournaments`
  - 联机大厅服务器审核通过 / 未通过 → `/servers`

  「发给谁」由业务自己决定，推送失败不影响主流程（`let _ = push(...)`）。
- 未读：两类相加；`POST /api/v1/notifications/read` 既推进水位，也把业务通知逐行标已读。
- UI：顶栏 `NotificationBell` 首屏数据由 layout 传入，打开时再拉一次；列表左侧徽章按 `kind`
  （评论 / 礼品卡 / 头衔 / 认证 / 赛事 / 联机 / 工单 / 系统）显示，未读时统一显示「新」。
- 浮层是**实底**（`--panel`），不使用 `--glass-*`：站内信是读文字的地方，半透明会让背后的帖子与签到卡透上来。

#### 工单（迁移 0033）

- 数据：`tickets`（分类 / 标题 / 状态 open·replied·closed / 时间）+ `ticket_messages`
  （role=user·admin·system，`author_id` 允许为空，兼容 ADMIN_TOKEN 应急通道）。
- 用户：`/tickets` 列表 + `/tickets/[id]` 时间线；「提交工单」弹窗（Portal 到 body），
  分类、标题 **2–80 字**、描述 **2–2000 字**；一人一天最多 10 张。
  校验没通过时按钮下方会写明「标题/描述至少 2 个字」，不是只把按钮置灰。
- 后台：`/admin/tickets` 左侧队列（待处理 / 已回复 / 已关闭）、右侧对话与回复；
  回复把状态推成 `replied` 并发站内信给用户；用户追问把状态推回 `open` 并通知所有管理员；
  关闭后用户不能再回复，只能重新打开或新建。
- 入口：前台侧栏「工作台 → 工单」，后台侧栏「社区 → 工单」。

#### 后台系统消息

- `/admin/messages`：发给单个用户（搜索昵称 / 用户名）或全站群发；全站会跳过已封禁账号。
- 复用 `notifications`（`kind=system`），所以用户端铃铛、通知页、未读计数自动生效；
  标题 2–40 字、正文 2–300 字、跳转地址必须是 `/` 开头的站内路径。
- 发送记录按收件人列出最近 50 条（含已读状态），便于确认发给了谁。

### 8.9.2 社区百科

站长维护的说明文档，与帖子完全分开：不走审核、不计积分、没有点赞。

- 表 `wiki_entries`（迁移 0043）：`slug` 唯一、`category` 存分类 key、`tags` 是 jsonb、
  `published` 区分草稿、`views` 记浏览。
- **分类可自定义**（迁移 0063）：`content_categories` 一张表管百科与资源库（`scope` 区分），
  `key` 是内容行里存的值（建好不改，资源库老数据就是中文分类名）、`label` 是展示名（随便改）、
  `descr` 一句话说明、`sort` 排序。0063 同时删掉 `wiki_entries` / `wiki_submissions` 上的
  `category IN (...)` 约束，并种入原有 5 + 8 个分类。
  - 公开读：`GET /api/v1/categories?scope=wiki|resource`；
  - 后台（`AdminActor`）：`GET/POST /api/v1/admin/categories`、
    `PATCH/DELETE /api/v1/admin/categories/{scope}/{key}`；`GET ...?scope=` 带内容数，
    `DELETE ...?moveTo=<key>` 用于「分类下还有内容」的情况（不带则 409，带上先在事务里搬内容再删）；
  - 写内容的接口（百科新建/修改/投稿、资源发布/修改）都改为对着表校验分类，不再有硬编码白名单。
- **投稿改了弹窗**：`WikiCompose` 把 `WikiEditor` 套进 Portal 弹窗（`variant` = btn / fab / text），
  Esc、点遮罩、取消都会关闭；有改动时先确认「内容不会保存」。`/wiki`、`/wiki/mine` 与词条详情的
  「编辑词条」都走弹窗，`/wiki/submit`、`/wiki/[slug]/edit` 仍保留为整页入口（深链与兜底）。
  编辑器自身在弹窗里用 `data-in-modal` 去掉卡片外框，分节滚动、底栏固定。

### 8.9.3 帖子版块与标签（迁移 0064）

- 版块落 `posts.section`（存 key），标签仍是 `posts.tags`（jsonb 数组）；两者都收进 `content_categories`，
  scope 用 `post_section` / `post_tag`，后台「内容 → 分类」多两个页签，可新建 / 改名 / 排序 / 删除。
- 发帖接口写库前校验：版块必须存在于表中（表为空时不拦，回落第一项）；标签最多 3 个、
  必须存在且自动去重。老帖子迁移时统一落到「常规」。
- 删除语义不同：版块跟百科 / 资源一样要先选迁移目标（`?moveTo=`，事务里 `UPDATE posts SET section`），
  标签没有迁移概念，直接在事务里用 `tags - 'key'` 从所有帖子摘掉。
- 前台：信息流支持 `/?section=常规` 筛选（页签下面是版块胶囊，横向可滚），帖子卡右上角显示版块，
  详情页的版块胶囊点回筛选；首页侧栏「热门标签」也改为读表。
- 公开接口：`GET /api/v1/wiki?category=&q=`（标题/摘要/正文 ILIKE，走 pg_trgm）、
  `GET /api/v1/wiki/{slug}`（浏览 +1，并返回同分类 4 条）。
- 后台接口（`AdminActor`）：`GET/POST /api/v1/admin/wiki`、`PATCH/DELETE /api/v1/admin/wiki/{id}`；
  后台列表**带正文**，编辑器不用再拉一次。
- 页面：`/wiki`（搜索 + 分类 + 卡片）、`/wiki/{slug}`（正文 + 本页目录 + 同类词条）、
  `/admin/wiki`（列表 + 弹窗编辑）。
- **历史版本**（迁移 0044）：`wiki_revisions` 存每次保存前的整份快照（标题/摘要/正文/分类/标签/编辑者）。
  - `PATCH /api/v1/admin/wiki/{id}` 在事务里先 `snapshot()` 再更新；
  - `GET /api/v1/wiki/{slug}/revisions` 公开列版本，`GET /api/v1/wiki/{slug}/revisions/{revId}` 取某版全文；
  - `PATCH /api/v1/admin/wiki/{id}/restore` 回滚（同样先快照当前内容，所以回滚也能再改回来）；
  - 页面 `/wiki/{slug}/history`：当前版本置顶 + 历史列表，`?rev=` 内联预览旧版，管理员可回滚。
- 列表页样式：条列式（一行一条，右侧分类色块当封面），顶部「全部条目 + 分类」下划线页签，
  管理员右下角有悬浮「+ 新建条目」。
- 标题锚点：`markdown.tsx` 的 `headingAnchor()` 给每个 h1–h3 生成稳定 id，同名标题自动加序号，
  右侧目录直接拿 `tocOf(body)` 的结果，两边算法必须一致。

### 8.9.6 信誉：初始 100，可人工扣除

- 总分 = `100 − 自动扣分 + 人工调整`，夹在 0–100；封禁直接 0。自动扣分只看被拒内容（每篇 −6，上限 −30）。
- 人工调整落表 `reputation_adjustments`（迁移 0046：`delta` / `reason` / `created_by`），
  接口 `GET|POST /api/v1/admin/users/{id}/reputation`，单次范围 −100…100、理由必填。
- 后台入口：`/admin/users` 每行的「信誉」按钮，弹窗里能看到当前分、档位、扣分说明与最近 30 条记录。
- 前台只显示汇总分与一句说明（如「管理员扣除 10 分」），不展示操作人。

### 8.9.14 上传：本地压缩与进度

服务端 `media::MAX_BYTES` 是 2MB，而且是在**收到完整请求之后**才判；手机照片常常 4–8MB，
以前直接被拒。现在所有图片入口都先在本机压一遍再传，公共实现是 `web/src/lib/upload.ts`：

- `compressImage(file, { maxEdge, maxBytes })`
  - 长边上限：头像 **512**，背景 / 正文 / 后台展示图 **1600**（与服务端 `MAX_WIDTH` 对齐）；
  - 优先转 **WebP**（不支持时退 JPEG），质量从 0.9 起按 0.1 递减，直到 ≤ 1.6MB；
  - **GIF 原样返回**：canvas 重编码会丢动画帧，超 2MB 时直接提示用户换图；
  - `createImageBitmap(..., { imageOrientation: 'from-image' })`，手机竖拍不会躺倒；
  - 压完反而更大（小图 / 已高压缩比）时保留原文件。
- `uploadWithProgress(url, file, { onProgress })`：XHR 实现，`fetch` 拿不到上传进度；
  统一返回 `{ ok, status, data, message }`，网络错误 / 超时 / JSON 解析失败都有兜底文案。
- 各入口的差异：
  | 入口 | 长边 | 反馈 |
  |---|---|---|
  | `/me` 头像 / 背景 | 512 / 1600 | 按钮显示「压缩中… / 上传中 45%」，完成后提示「2.7 MB → 617 KB（省 78%）」 |
  | 发帖 / 资源正文 | 1600 | 支持**多选、粘贴、拖入多张**，串行上传，按钮显示「2/3 45%」 |
  | 后台图片（奖品 / 卡面 / 关于） | 1600 | 预览框显示进度 |
  | 资源文件 | 不压缩 | 100MB/个、最多 8 个；支持**拖入文件区**（`data-drag` 高亮 + 「松开即可上传」） |

实测：2.68MB 的 2600×1800 照片作为背景上传 → 压到 617KB WebP（省 78%），服务端存储 631,304 字节。

### 8.9.26 禁言（迁移 0060）

### 8.9.9 移动端外壳与底栏常驻

底栏「跟着页面滑走」的根因不是 `position: fixed` 写错，而是**滚动发生在 body 上**：
移动浏览器（尤其 iOS Safari）滚动时地址栏收缩会改变视口高度，`bottom: 0` 的 fixed 元素
随之上下移动，看起来就像被页面拖着走。

所以移动端把滚动整体挪进外壳，底栏留在滚动容器之外：

```
body (height: 100dvh; overflow: hidden)
└─ .site-scroll (height: 100%; overflow-y: auto; -webkit-overflow-scrolling: touch)
   ├─ header.topbar (sticky)
   ├─ .app
   └─ footer
└─ TabBar (position: fixed)
```

- 只在 `@media (max-width: 860px)` 生效，且用 `body:has(.site-scroll)` 限定前台；
  后台外壳没有这个容器，行为不变。
- `100dvh` 带 `100vh` 回退；`overscroll-behavior-y: contain` 避免滚动链传到 body。
- 底栏去掉 `will-change` / `translateZ` / `backdrop-filter`：前两个在部分 WebView 里会让
  fixed 元素参与滚动重绘，`backdrop-filter` 与 fixed 组合在 iOS 上会重采样导致漂移；
  改成 `--panel` 实色 + 细边框。
- 5 个 tab 用 flex 均分，不再默认开横向滚动容器；只有配置超过 5 项时
  （`data-fits="false"`）才放开 `overflow-x: auto`。
- 频道标签行（首页 `.feed-tabs`）在 ≤860 去掉圆角卡片外壳，改成「页面底色 + 一条下划线」，
  跟内容衔接（两张不同材质的横条叠在一起会像两个工具条）。
  **不要再用负边距做通栏**：`margin-inline: -var(--app-pad)` 会让它左右各比卡片宽出
  14/16px，横向直接错位（用户看到的就是「这一行偏了」）；留在列内，左右与卡片严格对齐。
  实测 390 / 628 / 860 三档，标签行与 `.col-main` 的 left/right 完全一致。
- 副作用与配套：
  - Next 的滚动恢复只认 window → `ScrollReset` 在路由变化时把容器滚回顶部；
  - 抽屉打开时锁的是 `.site-scroll` 而不是 body（body 本来就不可滚）；
  - 页脚补 `padding-bottom: calc(78px + env(safe-area-inset-bottom))`，最后一行不被压住。

### 8.9.4 导航动效与玻璃层

- **侧栏 / 底栏的高亮是「游标」**：`Sidebar` 与 `TabBar` 各自量一次当前项的 `offsetTop/offsetLeft/size`，

- **毛玻璃只给浮层**：顶栏、侧栏、底部 tabbar、用户悬浮卡、下拉菜单、弹窗面板用半透明底 +

- **移动端**：底栏补 `env(safe-area-inset-bottom)`，内容区底部预留 92–96px 防止被遮；
  点击区最小 46px（tabbar）/36px（按钮）/32px（胶囊）；正文表格改为横向滚动容器；

  下发 `{ level, title, exp, floor, nextAt, progress }`；标题按段位取「新面孔 → 常客 → 熟面孔 →
  老玩家 → 社区骨干 → 资深玩家 → 社区元老」。
- **信誉**：0–100。基础 60，账号年龄最多 +10、发帖最多 +10、评论最多 +8、认证 +8，
  被拒内容每篇 -6（最多 -30），封禁直接 0。档位 优秀 ≥85 / 良好 ≥70 / 正常 ≥50 / 待观察 ≥30 / 受限。
- **下发位置**：`/api/v1/auth/state`（当前用户，顶栏与「我的」用）与 `/api/v1/users/{id}`
  （公开资料与悬浮卡用）都会把 `level`、`reputation` 塞进 user 对象，前端不需要额外请求。
- **展示**：`components/rank-badges.tsx` 的 `LevelPill` 参考 B 站等级牌——六边形裁切 + 段位渐变
  （Lv1 灰蓝 / Lv2 蓝 / Lv3 青 / Lv4 绿 / Lv5 紫 / Lv6 红）+ 白色「LV n」；`RepPill` 是圆点 + 分数，
  颜色跟档位；`LevelBar` 是「距下一级还差多少」的进度条。出现在 `/me`、`/u/{id}` 与用户悬浮卡。

### 8.10 多渠道登录

支持三种方式，最后都归一成同一个会话 Cookie：

| 方式 | 入口 | 说明 |
|---|---|---|
| 用户名 / 邮箱 + 密码 | `POST /api/v1/auth/login` | `identifier` 带 `@` 当邮箱，否则先查用户名再兜底邮箱 |
| GitHub | `GET /api/v1/auth/oauth/github` | OAuth App，scope 只申请 `read:user` |
| CNKD 一证通行 | `GET /api/v1/auth/oauth/cnkd` | OAuth 2.0 + PKCE(S256)，scope `profile.basic profile.status` |

```
浏览器 ──▶ /api/v1/auth/oauth/:provider
             │ 生成 state + PKCE，写 httpOnly Cookie（10 分钟）
             ▼
        平台授权页（GitHub / cloud.cnkd.fun/account/oauth/authorize）
             │ 用户同意，带 code & state 回跳
             ▼
        /api/v1/auth/oauth/:provider/callback
             │ 校验 state（Cookie 与 URL 必须一致）
             │ 服务端换 token → 取资料 → 找绑定 / 建号
             ▼
        写 ba_session，跳 /me
```

#### 给已有账号绑定第三方

登录页走的是「找绑定 → 没有就建号」，而 `/me → 登录方式` 走的是**绑定**：

- 入口是 `GET /api/v1/auth/oauth/{provider}?bind=1`，必须已登录（未登录会跳 `/login`）。
- 绑定意图写在一次性 Cookie 里：`oauth_state=provider.state.1`（最后一段 `1` = 绑定模式），
  回调据此分流 —— 绑定模式**不发新会话、不建号**，只往 `identities` 插一条记录。
- 该第三方已被别的账号绑走时返回 `/me?bind=taken`；成功后 `/me?bind=ok`；
  中途失败回 `/me?bind=error&code=...`，不再把已登录的人踢回登录页。
- 同一账号同一平台只能绑一个（迁移 0041 的 `identities_user_provider` 唯一索引），
  重新绑定会覆盖成新身份。
- `DELETE /api/v1/me/identities/{provider}` 解绑；**没设密码又只剩这一个登录方式时拒绝**，
  否则这个人就再也登不进来了。
- 「我的」页的 `LoginMethods` 卡片会显示：用户名密码是否已设置、各平台的绑定状态与
  绑定 / 解绑按钮；后台没配 Client ID 的平台显示「未开放」。

**四个不能改错的点：**

1. **`sub` 才是唯一键**。GitHub 用 numeric id，CNKD 用 UUID `sub`；不能用用户名或昵称，
   对方允许改名，改名就会变成两个人。
2. **回调地址必须与平台登记完全一致**，后台「站点设置」里直接显示要填的地址
   （`{对外地址}/api/v1/auth/oauth/{provider}/callback`）。
3. **注册开关只拦新建**：已绑定的老用户即使站点关闭注册也能登录，否则等于把老用户锁在门外。
4. **纯第三方账号没有密码**（`passwordHash` 为空串），`authenticate()` 会直接拒绝密码登录。

`server/src/routes/oauth.rs` 的 `provider_enabled()` 判断「ID + Secret 都填了」才在登录页显示按钮，
不会出现点了报错的按钮。失败一律回到 `/login?error=xxx`，页面把错误码翻成中文。

### 8.11 徽章系统

和「头衔」是两件事：

| | 头衔 | 徽章 |
|---|---|---|
| 数量 | 一人一个 | 一人多个 |
| 来源 | **申请 + 后台审核** | 规则自动判定 |
| 位置 | 作者名后 | 个人主页、作者卡片 |

**头衔不再由用户直接改**（`PATCH /api/v1/me` 会返回 422 `title_requires_review`）：

- 用户在「我的 → 头衔」提交文案 + 样式 + 特效 + 说明（迁移 0029 `title_requests`），
  一人同时只能有一条 `pending`（部分唯一索引兜底），被拒可改了再提；
- 后台 `/admin/titles` 审核：通过时可以改文案、样式、特效，最终写进 `users.title/title_style/title_effect`；
- 申请与审核结果都会发站内信。
- **公开接口必须带上外观**：`PublicProfile`（`/api/v1/users` 与 `/api/v1/users/{id}`）要下发
  `title_style` / `title_effect`（camelCase 即 `titleStyle` / `titleEffect`）。少了这两个字段，
  `badgeOf()` 只能按兜底值渲染成默认蓝，看起来就像「申请时选的样式没生效」——而库里其实是对的。
  帖子里作者名后的头衔也读同一份映射（`getBadgeMap()`），所以这一处漏了会全站一起丢样式。
- 头衔只在名字后面画一次（`NameBadges` → `VerifyMark` / `UserBadge`）；个人主页的 `.up-meta`
  不要再放一枚灰色 `badge-ghost` 副本，否则同一个人会同时出现「带样式的」和「灰的」两个头衔。

#### 蓝标 / 红标认证（迁移 0032）

认证和头衔是两条线：头衔是展示文案，认证是**平台对身份背书**，所以不能自设、也不带样式选项。

| | 蓝标 | 红标 |
|---|---|---|
| 对象 | 个人：创作者、服主、模组作者 | 机构：公会、战队、开发团队、媒体 |
| 形状 | 圆形对勾 | 八角星对勾（不靠颜色也能分辨） |
| 存储 | `users.verify_kind = 'blue'` | `users.verify_kind = 'red'` |

- 用户侧：「我的 → 认证」提交认证主体、类别、证明材料（≥10 字）与联系方式，
  一人同时只能有一条 `pending`；通过后 `users.verify_label` 存对外说明（≤20 字，鼠标悬停展示）。
- 后台侧：`/admin/verifications` 审核，通过时可以改类型（蓝标申请按红标批也允许）与说明；
  「直接授予」面板给官方 / 合作方账号跳过申请，走 `PATCH /api/v1/admin/users` 的
  `verifyKind` / `verifyLabel`，传空串即取消（说明与时间一并清掉）。
- 展示：`components/verify-mark.tsx`，由 `NameBadges` 统一插在名字后面（名字 → 印记 → 头衔 → 身份组），
  帖子卡、楼层、悬浮名片、页头自动都有；颜色只走 `--blue` / `--seal-red` 两个令牌。
- 通过 / 未通过都会发站内信（`kind=verify`）。

样式是**枚举键**（`plain / blue / gold / violet / mint / solid / outline / holo`），
特效是 `'' / shine / glow / pulse`，色值只在 CSS 的 `[data-bs="…"]` 里定义一次，
头衔（`.ut`）与徽章（`.bz`）共用这套调色板；身份组颜色由后台自填，按 `soft / solid / outline / glow`
四种处理方式渲染（`.gtag[data-gs]`）。

规则写在 `lib/achievements.ts` 的 `CATALOG`，判定只读 users / forum / sponsors 三份数据，
`getAchievementMap()` 用 React `cache()` 做请求内缓存，列表页一次读盘就能渲染所有作者。

> 后端已有一份等价实现：`server/src/achievements.rs`（同一份 8 条规则，读 users/posts/comments/sponsors），
> 对外是 `GET /api/v1/achievements`（全站表）与 `/api/v1/achievements/{userId}`（单人进度）。
> 切换后前端改用这两个接口，规则以 Rust 为准；两边的目录必须同步改。

当前目录：创始成员、管理员、初次发声、笔耕不辍（10 篇）、热心回复（20 条）、
人气作者（50 赞）、赞助者、元老（注册满 30 天）。

每个徽章的样式可以在后台 `/admin/appearance` 覆盖（`badge_styles` 表，按 badge_id 存），
接口 `/api/v1/achievements` 直接把 `style` / `effect` 带在每一项里，前端不再按 `tone` 硬编码颜色。

新增徽章只改 `CATALOG` 一项，判定与展示会自动跟上；要落库的自定义徽章走
`users.json` 的 `badges` 字段（`setUserBadges()`，暂未开放后台界面）。

### 8.12 内容审核（AI 预审）

`postAuditMode` 三个值：

| 值 | 行为 |
|---|---|
| `off` | 发帖即发布 |
| `ai` | 先调 AI：模型判定 `risky=false` 直接发布；`true` 或调用失败进待审 |
| `all` | 全部进待审，只由人工放行 |

- 实现：`server/src/audit.rs`（`ai_config` / `ai_review` / `precheck`），走 OpenAI 兼容的
  `POST {baseUrl}/chat/completions`，请求带 25 秒超时、`temperature: 0`。
- 配置在「站点设置 → 内容审核」：`aiBaseUrl` / `aiApiKey` / `aiModel`（默认 `gpt-4o-mini`）/
  `aiPrompt`（留空用内置规则）。密钥只存库、不写日志，也不进公开设置。
- 模型必须输出 JSON：`{"risky":bool,"score":0-1,"labels":[],"reason":""}`；
  回复被 ```` ```json ```` 包住或前后带解释也能抠出来，实在解析不了就按调用失败处理。
- **没配密钥、上游报错、返回非 JSON 一律进待审**，不放行：宁可多一条人工，
  也不要把可疑内容直接放出去。
- 自测：`/admin/audit` 的「测试 AI 配置」，会带一句固定文案跑一次并把上游错误原样显示出来，
  方便排 `baseUrl` / `key` / `model`。
- 审核结果写 `audit_logs`（`source=ai`），人工复核页 `/admin/audit` 不变。
- **历史值兼容**：上一版接腾讯云时写入的 `tms` 仍按 `ai` 处理（不会静默关掉审核）；
  后台打开设置保存一次就会归一成 `ai`。腾讯云的 `tmsSecret*` 配置项已移除，库里残留的键不再读取。

### 9.1 浏览器推送（Web Push）

不依赖第三方推送服务，直接用 VAPID + aes128gcm：

| 层 | 实现 |
|---|---|
| 前端 | `public/sw.js`（只做通知展示与点击跳转，不做离线缓存）+ `components/push-toggle.tsx` |
| 后端 | `server/src/push.rs`：ECDH P-256 → HKDF → AES-128-GCM 加正文；ES256 JWT 放进 `Authorization: vapid t=…, k=…` |
| 存储 | 迁移 0019：`push_subscriptions`（endpoint 唯一）、`push_messages`（发送记录） |

- 密钥对在首次调用 `/api/v1/push/key` 或后台概览时生成，写进 settings 的
  `vapidPublicKey` / `vapidPrivateKey`；**换服务器要连库一起迁移**，否则已订阅设备全部失效。
- 订阅入口：`/me` 的「通知」卡片、后台顶栏的推送按钮、`/admin/push` 的开关。
- 推送失败语义：404 / 410 视为订阅已失效并直接删除；其它失败累加 `fail_count`，
  后台可「清理失效订阅」。
- 受众：`all` / `signed_in`（绑定了账号）/ `admins`。
- iOS 只有「添加到主屏幕」后才支持；浏览器不支持时按钮会直接说明原因，不做假开关。

**三条防锁死规则**（`api/v1/admin/users` 里实现，不要绕过）：

1. 不能改自己的角色、封禁自己、删自己；
2. 任何操作后必须至少剩一个**可用**管理员（`role=admin && !banned`）；
3. 应急口令（无会话）可以操作，但同样受规则 2 约束。

封禁是**全局生效**的：`getCurrentUser` 解析会话后检查 `banned`，被禁账号的旧 Cookie 直接作废，登录接口返回 403 `account_banned`。

覆盖：健康与数据目录可写、9 个页面 200、bootstrap 无占位域名、调试页已关、后台鉴权三态、安全响应头。

## 12. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 页面样式全丢 | 检查 `globals.css` 是否被 `layout.tsx` import；dev 下改 CSS 需等 HMR |
| 主题切换后刷新又变回去 | cookie 没写成功（`path=/` 缺失或被浏览器拦） |
| 移动端看到桌面布局 | `--window-size` 太小但 headless 有最小窗宽（约 500px）；真机不受影响 |
| 构建卡住不动 | 产物目录被文件守卫拦批量删除；换新 `NEXT_DIST_DIR` 或提高阈值 |
| 微信内判断错 | 看响应头 `x-wechat` 与 `x-form`，再看 `/dev/capabilities` 的 source |
| 后台在手机上打不开 | 已取消 403；若仍 403，检查是否有旧 middleware 缓存 |
| 部署后 `/api/health` 返回 503 | 数据目录不可写（卷权限）。容器内 uid 是 1001：`chown -R 1001:1001 <卷>` |
| 上传报 413 | 反代 `client_max_body_size` 太小，调到 2100m |
| 分享链接指向 localhost | 反代没透传 `Host` / `X-Forwarded-Proto`；或在后台「对外地址」写死了 localhost |
| 后台一直停在登录页 | `ADMIN_TOKEN` 里的 `$`、空格被 shell 展开；用单引号包值或用 `openssl rand -base64 24` |
| `node server.js` 起来但页面无样式 | standalone 漏拷 `.next/static` 与 `public` |
| 接口 500：`cookies was called outside a request scope` | 在 Route Handler 里调了被 `cache()` 包住的 `getCurrentUser()`；改用 `getCurrentUserFrom(req)` / `isCommunitySignedFrom(req)` |
| 注册页没有验证码 | `GEETEST_ID` / `GEETEST_KEY` 没配；补上后重建。未配时会跳过校验并在页面提示 |
| 一直是「第一个用户」提示 | 数据目录被清空或卷没挂住；检查 `DATA_DIR` 与卷挂载 |
| GitHub / CNKD 登录报 `redirect_uri_mismatch` | 平台登记的回调地址与后台显示的不一致；把后台「站点设置」里的回调地址复制过去重新登记，注意 https 与路径大小写 |
| 第三方登录后是新账号 | 该平台账号第一次登录，或换了平台的另一个账号（`sub` 不同）；属正常行为，同一平台账号不会重复建号 |
| 徽章不更新 | 规则按全站数据实时算，页面有请求内缓存；刷新即可，新发帖后当前请求内可能还是旧值 |
| 详情页明明显示 404 页，状态码却是 200 | 该路由段上有 `loading.tsx`，headers 已提前 flush；见 §5.1，把 loading 移到 `(list)` 组或不放 |

## 13. 部署：自托管

**不依赖任何托管平台**，产物是一个 Node 进程 + 一个可写目录。完整手册见 [`自托管部署.md`](./自托管部署.md)。

```
浏览器 ──TLS──▶ nginx/Caddy ──▶ node server.js ──▶ $DATA_DIR/*.json
```

要点：

- `next.config.mjs` 开了 `output: 'standalone'`，容器里只带 `server.js` + `.next/static` + `public`，镜像约 180MB。
- 构建阶段固定 `NEXT_DIST_DIR=.next`；本地的 `.dist/.out` 那套只是为了绕开文件删除守卫，与部署无关。
- **`.env` 只放进程参数与密钥**：`PORT` / `DATA_DIR` / `SESSION_SECRET` / `ADMIN_TOKEN`；
  业务配置（站点名 / 人机验证 / 爱发电 / 注册开关）在后台，改完立即生效。
- 对外地址按「后台设置 → 环境变量 → 请求头」三级推导；Cookie 的 `Secure` 直接看请求 proto，不依赖配置。
- 之前写死的 `*.blockarena.example` 已全部清掉。
- 健康检查 `/api/health`：返回数据目录可写性，`unwritable` 时给 503，供 Docker healthcheck 与反代探活。
- 部署后必跑：`ADMIN_TOKEN=xxx bash scripts/selfhost-check.sh https://你的域名`（健康、9 个页面、占位域名、调试页、鉴权三态、安全头）。

单实例限制：文件存储没有跨进程锁，**不要起多副本**；要横向扩容先把 `lib/json-store.ts` 换成数据库。

> 前后端分离的目标形态是 **nginx + 三个进程**（`web` 渲染、`api` 业务、`db` PostgreSQL），
> 编排按容器分开放：`server/compose.yml`（db + api）、`web/compose.yml`（web）。
> `db` 不发布端口，`api` healthcheck 用自带子命令。
> **当前形态已经是三容器**：`web` 通过 `API_BASE` 内网取数，`api` 连 `db`。
> 部署步骤、备份/恢复、压测与慢查询见 [`自托管部署.md`](./自托管部署.md) §0；
> 下面 §13 余下内容是分离前的单进程部署，留作历史参考。

## 14. 前后端分离：Next + Rust + PostgreSQL（已落地）

完整蓝皮书：[`前后端分离方案.md`](./前后端分离方案.md)。本节只写结论与红线，
避免两处文档各自漂移——**细节以方案文档为准，本节的阶段表是唯一进度看板**。

### 14.1 定下来的五件事

| 项 | 结论 |
|---|---|
| 前端 | **不重写**。Next.js 15 继续做 SSR、样式、交互、端能力（`lib/capabilities.ts` 留在 TS） |
| 后端 | Rust（axum）独占 `app/api/v1/**` 对应的能力：会话、鉴权、业务、外部集成 |
| 数据库 | **PostgreSQL 18**（当前稳定线；19 于 2026-11-19 GA，暂不追） |
| 分离方式 | **路径分离**：同域名 `/api/*` 直连 Rust，其余走 Next。不引入 CORS，Cookie 不改 `SameSite` |
| 数据迁移 | `$DATA_DIR/*.json` → PG 一次性导入（单事务 + `--dry-run` 校验），**不做双写** |

```
浏览器 ──TLS──▶ nginx ─┬─ /api/* ─▶ Rust :8080 ─┬─▶ PostgreSQL :5432
                       └─ 其余   ─▶ Next :8900 ─┘（内网取数，不绕公网）
```

> 为什么不是 SQLite：只适合单机单写、备份靠 `.backup`、跨主机无法共享。既然目标是独立可扩的后端，直接上 PG。
> 为什么不是 `api.example.com`：那会强制 Cookie 改 `SameSite=None` 并引入 CORS 白名单，削弱现有 CSRF 防护；
> 「独立部署」靠 nginx 路径分流就能实现，不需要换域名。

### 14.2 边界判定规则

**「谁拥有事实」进 Rust，「事实怎么呈现」留 Next。**

| 进 Rust（含 PG） | 留 Next |
|---|---|
| 用户 / 会话 / 密码 / 身份绑定 | 端能力（runtime / form / isWeChat）、`bootstrap` 与 ETag |
| 帖子 / 评论 / 点赞 / 公约签署 | 徽章与头衔的**渲染** |
| 公告 / 轮播 / 站点设置 | 相对时间（「3 分钟前」）、分页文案等派生展示 |
| 赞助者快照 / 爱发电同步 / 站内信聚合 | 空态文案、全部 CSS |

> 直接后果：Rust **不返回** `time: "3 分钟前"` 这类字段，只返回 `createdAt` 毫秒；
> `forum-store.ts` 的 `relTime()` 迁移到 Next 侧。这是本方案唯一会改动前端数据形状的点。

### 14.4 七条兼容红线（做错就等于事故）

1. 会话 token 仍是 `<userId>.<exp 秒>.<base64url(HMAC-SHA256)>`，签名入参是拼接后的文本；
2. `SESSION_SECRET` 缺失时**必须复用** `$DATA_DIR/.session-secret`，Rust 不能另生成一个；
3. 密码哈希串 `scrypt$N$r$p$<base64 盐>$<base64 key>` 用**标准 base64**，参数从串里解析；
4. Cookie 属性照抄：HttpOnly / SameSite=Lax / Path=/ / 7 天 / `Secure` 只看请求 proto；
5. 错误响应 `{error, message}` 的错误码与中文文案逐条对齐；
6. **时间**：DB 存 `timestamptz`，但 API 出口必须转毫秒整数，契约不变；
7. JSON 键 camelCase，`Option::None` 要 `skip_serializing_if`（对应 TS 的 `undefined` 不出现）。

PG 专属的三条：

- 迁移脚本**只增不改**（`0001`、`0002`…），改历史会导致已在跑的环境 schema 漂移；
- 首个 admin 用 `pg_advisory_xact_lock` + 事务，别用「先查后插」；
- 金额用 `numeric(12,2)`，读出来再转 f64，避免浮点尾巴进 JSON。

> 落地手段：把现在 Node 生成的「一个 passwordHash / 一个 session token / 一段 users.json」
> 写成 Rust 侧的 golden fixture，`cargo test --test compat` 不过就不许发版。

## 15. 资源库、开发团队与开发者身份

### 15.1 三种组织，互不隶属

| 组织 | 面向 | 榜单口径 | 表 |
|---|---|---|---|
| 公会 | 社区组织 | 积分 → 胜场 → 少负 | `guilds` |
| 战队 | 约战队伍 | 同上，单独一张榜 | `teams` |
| 开发团队 | 资源作者 | 资源数 × 4 + 下载 + 点赞 × 3 | `dev_teams` |

**不要**给开发团队加 `guild_id`，也不要在文案里写「下属团队」。
三者的负责人可以重合，但身份互不影响。

### 15.1b 资源库首屏（参考资源广场）

- 顺序：搜索 → 分类 → 游戏 → 数量 → 最近更新 → 卡片网格。
  **分类是主维度**（`content_categories(scope=resource)`），游戏是二级筛选，不要倒过来。
- 分类胶囊带数量：`GET /api/v1/categories?scope=resource&counts=1`，只统计已发布资源。
- 搜索是页面内 `<form action="/resources">`，提交时把 `game` / `category` / `sort` 带上，
  不丢当前筛选；排序仍是「最新 / 最多点赞 / 最多下载」三枚胶囊。
- 「最近更新」只在第一页（没有 q / game / category 且 sort=new）出现，横向 6 张，避免和下面网格重复。
- 宽屏（≥1400px）网格从两列变三列，卡片不至于被拉成一条。
### 15.1c 外部来源站（迁移 0065）

- 资源不再只能是本站上传：Minecraft 可以指向 **CurseForge / Modrinth**，铁锈战争指向 **rtsbox**
  （`www.rtsbox.cn`，条目形如 `/11149-2`）。库里只存三列：
  `source`（站点）、`source_id`（项目标识）、`source_kind`（类型）。
- 站点与游戏的对应关系写死在 `resources::sources_for()`，校验也在那里：
  MC 挂 rtsbox 会被拒（「这个游戏暂不支持该来源站点」）。
- **链接生成规则**要按站点分开（`kind_path()`）：CurseForge 是 `mc-mods` / `modpacks` / `texture-packs`，
  Modrinth 是单数 `mod` / `modpack` / `resourcepack`；rtsbox 直接 `/{id}`。
- 用户**粘贴整条链接**时原样保存（`split_source_ref()` 只从末段取标识），不再用规则去猜；
  只填标识时才按上表拼。
- 主地址优先级：手填下载地址 → 粘贴的来源链接 → 拼出来的来源链接 → 第一个附件
  （`canonical_url()`）。前端 `resource-types.ts` 里有一份等价实现，用于表单实时预览。

### 15.1c2 从外部站点直接拉取

- `GET /api/v1/resources/discover?source=modrinth|curseforge&kind=&q=&limit=`：
  走官方 API 搜索，标准化成 `{ source, sourceId, title, summary, author, icon, downloads, url,
  kind, projectId }`。
- `POST /api/v1/resources/import`：把条目落库（作者=当前用户，`status=published`，分类按类型建议，
  `source/source_id/source_kind` 一并写入）。落库前会再拉一次项目详情，把**介绍正文、加载器、
  支持版本、授权、标签、封面**一起写进去 —— 收录后的条目和站内自己发布的一样完整。
  同一个 `(source, source_id)` 只收一次，重复点直接返回已有 id（`existing: true`）并跳过去。
- 三个站的现实：
  - **Modrinth** 公开 API，免 key，直接可用（`User-Agent` 必带）。
  - **CurseForge** 需要 key，后台「站点设置」填 `curseforgeKey`；没配时接口返回可读原因，前端提示去配置。
  - **rtsbox** WordPress + 反爬：非浏览器请求只回占位页（`<h1>API 接口文档`），`/wp-json` 也 403，
    所以**不提供在线拉取**，用「粘贴链接」建条目（`source=rtsbox`）。
- 前端**不再单独开板块**：外部条目由 `RemoteCells` 直接渲染进资源库同一个 `.res-grid`，
  卡片与站内资源同款（大图封面 / 标题 / 两行简介 / 版本·加载器·分类胶囊 / 版本号 + 下载量），
  整张卡是按钮，**点一下即收录**并跳到详情页；来源站只在卡片上留一枚蓝色「Modrinth」胶囊。
- 只有 Minecraft 板块混入外部条目；切到铁锈战争或按分类筛选时整块不出现（远程条目没有本站分类，
  混进来会让筛选结果说不通）。搜索框同时作用于外部站：有 `?q=` 就按词搜，没词取热门。
- 详情页侧栏固定一块「来源」，写明「介绍、封面与版本信息来自原站，本站只做收录与索引」，
  标题下方的「来自 Modrinth ↗」徽章可点回原条目。

### 15.1c3 铁锈战争：rtsbox 模组 + RELAY-CN 地图

两个站的参数规则不一样，别当成一套：

- **模组（rtsbox）**：`POST https://www.rtsbox.cn/api/search_bbs.php`，表单
  `bbs_id=4`（模组；地图是 5）、`page`（**从 1 开始**）、`keyword`（**必填**）。
  关键词为空时它不返回 JSON，而是一张「暂没有数据」的 HTML 空状态页 —— 所以前端
  没输入关键词时这一栏直接不出现，并给一句提示。返回 `{ title, downurl, img, bbsurl }`，
  没有简介与版本，`source_id` 取 `bbsurl` 末尾的数字。
- **地图（RELAY-CN 地图站）**：`GET https://maps.rw.nebulapause.com/api/mapLists.php`，
  `Authorization: Bearer <后台设置里的 rwMapsToken>`，用 `type` 分发：
  - `search`：`nameKey` / `page` / `pageSize`（≤100）；实测**经常回 400「禁用」或 503
    （上游认证超时）**，所以搜不到时自动回落 `random`；
  - `random`：`count` 1–10，无需关键词，用来铺「没搜的时候」那一屏；
  - `get`：`id`，拿单条详情（含签名下载链接）；
  - `batch` 一直禁用，不要依赖它翻页。
- 记录字段：`id`、`thumbnail_url` / `image_url`、`map_metadata.filename`（地图名）、
  `map_type`、`player_count`、`map_metadata.resource_pool_count`（矿点）、
  `map_metadata.image_width/height`（像素尺寸）、`download_count` / `like_count`、`created_at`（秒）。
- 卡片上的标签是**自己组**的（玩法 / 人数 / 矿点 / 尺寸），不用 `map_tags` ——
  那里混着触发器分类（检测 / 事件 / unitAdd…），对玩家没意义。
- **下载**：`download_url` 是签名链接，绑定取签名时的 IP/UA、120 秒过期，交给浏览器也打不开。
  所以走本站 `GET /api/v1/rw/maps/{id}/download` 转发（服务端拉流，不落盘）。

接口（都在 `/api/v1/rw/` 下）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/rw/discover?q=&page=&limit=` | 一次返回 `{ mods, maps, modError, mapError }`，两边互不影响 |
| GET | `/rw/maps/{id}/download` | 转发地图包（`Content-Disposition` 带文件名） |

### 15.5 开发者榜计分

- 个人：`score = Σ(download_count) + 3 × Σ(like_count)`，只统计本人署名的资源。
- 团队：`score = 资源数 × 4 + 下载 + 点赞 × 3`，只统计 `team_id` 指向该团队的资源。
- 同分依次看下载、点赞、加入时间；0 资源不进榜。

### 15.7 资源多文件（迁移 0023）

- `resource_attachments` 引用 `resource_files`（用户上传记录），一个资源最多 **8** 个文件；
  文件本身不复制，删除资源只级联删附件行，上传记录仍在。
- `POST /api/v1/resources` 与 `PATCH` 接受 `fileIds: string[]`（顺序即展示顺序）；
  只挂当前用户上传的文件，别人的 id 会被跳过。`PATCH` 传了就**整组替换**，不传保持原样。
- `resources.url` 仍是主地址：只上传文件没填外链时，服务端自动指向第一个附件，
  老的单文件下载入口继续可用。
- 详情接口下发 `files`（含 `id` / `fileId` / `name` / `size` / `downloads` / `url`）与 `fileCount`；
  列表只带 `fileCount`，卡片显示「N 个文件」。
- 发布弹窗支持一次多选，串行上传并显示「第几个 / 共几个」；已在列表里的可单独移除。
- 文件区可以直接把文件拖进来（`data-drag` 时高亮并提示「松开即可上传」）；

## 16. 福利中心：礼品卡 / 兑换码 / 抽奖

### 16.1 一张表三种形态

`gift_cards` 用 `kind` 区分：

### 16.2 原子性

发奖与扣分必须同事务：

- `points::award_in(&mut tx, ...)` 在调用方事务里写 `point_logs` 并更新 `users.points`；
- **删除内容必须冲正**：`points::revoke_in(...)` 与删除动作同一个事务，写
  `post_revoke / comment_revoke / resource_revoke`。没有这一步时「发布 +20 → 删除」
  可以无限刷分（20 分正好一次抽奖）。
  - 删帖：先统计该帖评论作者（外键会级联删评论），再冲正发帖分与每人评论分。
  - 删楼 / 删资源：按作者冲正 2 / 20 分。
  - 只扣到余额为 0 为止，并按**实际扣除额**记账，保证 `sum(delta) == users.points`。
  - 自己给自己的帖子评论不发分（否则「发帖 → 自评 → 删帖」同样能刷）。
- 拆卡 / 兑换 / 抽奖都先 `SELECT ... FOR UPDATE`，再标记已用 + 发奖 + 提交；
- 抽奖余额不足直接回滚，不写流水；限量奖品用 `UPDATE ... WHERE stock > 0` 防超发。

### 16.3 抽奖

- 单次 `LOTTERY_COST = 20` 积分（`rewards.rs` 常量）。
- 奖池表 `lottery_prizes`：`kind=points|gift|custom|none`，`weight` 权重，`stock` 为空表示不限量。
- 抽奖记录 `lottery_draws` 保留奖品名与消耗，便于回溯。
- 前端抽奖有滚动动画；中奖后复用礼品卡获得特效（全屏遮罩 + 卡片弹入 + 粒子）。
- **自定义奖品**（`kind=custom`）连同名称 / 说明 / 图片一起展示，并自动生成一张 `reward_kind=custom` 的礼品卡。
- **奖品图片**：后台直接本地上传，不必先把图传到别处再粘链接。
  - 走 `POST /api/v1/me/media?kind=reward`（迁移 0048 给 `user_media.kind` 增加 `reward`），
    **只有管理员能传**，普通账号返回 403；上限 2MB，按魔数判 PNG / JPEG / WebP / GIF。
  - 返回 `/api/v1/media/{id}`，写进 `lottery_prizes.custom_image` / `gift_cards.reward_image`。
  - 后台 `PATCH /api/v1/admin/rewards/prizes/{id}` 支持 `customImage`（空串清空），
    于是奖池里已有的奖品可以直接换图，不用删掉重建（权重与库存不会丢）。
  - 前端上传器是 `components/reward-image-picker.tsx`：预览框可点、可移除，也保留「用外链」入口。
- 展示：中奖弹窗里的图按 `object-fit: contain` 完整显示（方图用 `cover` 会被裁成一条横带），
  奖池列表有图时用缩略图代替色点。

  能力（中文标签）与进组需签署的公约。

- 前端 `GroupTag`：帖子、评论、顶栏、个人中心、后台用户表统一使用；`/groups` 是公开说明页。
- 内置组：成员（默认）、管理员、开发者。删除自定义组时成员自动回落默认组。

## 18. 用户上传与 Markdown 编辑器

### 18.1 图片上传（头像 / 背景 / 帖子配图）

迁移 `0012` 新增 `user_media`：

```sql
user_media(id, user_id, kind, mime, bytes, size, created_at)
users.avatar text NOT NULL DEFAULT ''
```

- 默认图片存 `bytea`：`pg_dump` 一份备份就能带走，分享图也不会跨域。
- 迁移 `0014` 增加对象存储：`user_media.storage` / `object_key`，`bytes` 可为空。
  后台「站点设置 → 对象存储」可选 `db` / `s3`，支持阿里云 OSS 与雨云 ROS（都是 S3 兼容）。
  配置：Endpoint / Region / Bucket / AccessKey / SecretKey / 路径前缀 / Path-Style，
  带「测试连接」（写入并删除探针）。切换后新图走桶，旧图仍可读；桶可保持私有，
  `/api/v1/media/{id}` 由后端代理，避免公开桶和跨域。
- 单张上限 **2MB**；只认魔数（PNG / JPEG / WebP / GIF），不信任 `Content-Type`。
- `POST /api/v1/me/media?kind=avatar|background|post`，请求体是图片字节本身；
  `avatar` / `background` 会同时更新用户字段，并删掉上一张本站图片。
- `GET /api/v1/media/{id}[?w=]` 公开读图，`Cache-Control: immutable` + `ETag`。
- 头像在顶栏、我的页、帖子卡、帖子详情与评论中显示；空值回落昵称首字。

### 18.1b 对象存储（含资源文件）

- 开关仍是「站点设置 → 对象存储」的 `storageDriver = s3`，配好 Endpoint / Region / Bucket /
  AccessKey / SecretKey 即生效；图片（头像、背景、正文图）与**资源附件**都走同一套配置。
- 资源附件（迁移 0038）：`resource_files.storage`（fs / s3）+ `object_key`；
  上传用 `BufWriter` 流式写桶（最大 100MB 不进内存），下载按 storage 分流并流式回传。
- 后台「内容 → 文件管理」(`/admin/files`)：图片与资源文件分页列出，显示上传者、大小、
  存储后端；删除时同时清对象存储里的原件与数据库行。
- 本地模式（未配桶）继续落 `$DATA_DIR/uploads/resources/`，两种模式对前端是同一套 URL。

#### 缩略图（迁移 0035，2026-10-28）

原图直出时一个 33px 的头像要塞 400KB、封面 1.3MB，首屏要等 4–9 秒。现在按「媒体 + 宽度」缓存缩图：

- 表 `media_variants (media_id, width, mime, bytes, size)`，外键级联删除，删原图不留垃圾。
- **头像即使不带参数也按 256px 出图**（`AVATAR_WIDTH`），所以老页面不改代码也一起变快；
  其它类型默认出原图，需要小图时显式带 `?w=`（32–1600，超界夹到边界）。
- 头像居中裁正方形（`resize_to_fill`），其它图等比缩放；有透明通道编 PNG（最高压缩 + 自适应滤波），
  不透明编 JPEG q82。
- **缩完反而更大就回落到原图**：原图本来就被压得很狠时，换小图没有意义。
- GIF 是动图，缩放只剩第一帧，原样返回。
- 请求先查 `media_variants`，命中就直接返回，不碰原图（S3 上省一次跨网络读取）。
- 前端 `lib/media.ts` 的 `mediaUrl(url, width)` 只对 `/api/v1/media/` 前缀加参数，
  外部图床原样返回；正文配图 1280、赛事封面 960（列表 640）、个人背景 1600。
- 结构化数据：帖子页输出 `DiscussionForumPosting`（作者、发布时间、点赞/回复计数），
  资源页输出 `SoftwareApplication`（免费、按游戏分类），新闻页输出 `NewsArticle`（栏目、封面、发布者），
  百科页输出 `DefinedTerm`（挂在分类的 `DefinedTermSet` 下），赛事页输出 `Event`（时间 / 线上场地 / 主办方，
  草稿不输出）；站点级输出 `Organization`，各详情页再补一条 `BreadcrumbList`。
  序列化统一走 `jsonLdString()`，会把 `<` 转义成 `\u003c`，正文里出现 `</script>` 也不会截断。
- sitemap 追加赛事详情（草稿除外）、开发团队、任务、关于、更新日志；robots 继续由后台开关控制。

- 反向代理可用 `deploy/nginx-media-cache.conf`：`/api/v1/media/` 直接打后端并落 nginx 缓存，
  同一张图跨用户只回源一次；`X-Cache-Status` 可看命中情况。

#### 渐进式加载（`components/smart-image.tsx`）

- 占位：先请求 `?w=32` 的小图，铺满后用 `blur(20px)` 做同色调底（主色来自小图本身）。
- 过渡：原图加载完成后 500ms 内从模糊变清晰，同时 `scale(1.04) → 1`；`prefers-reduced-motion` 下直接显示。
- 尺寸：`user_media.width/height` 在上传时写入；正文渲染前用 `GET /api/v1/media/sizes?ids=…`
  批量取（最多 24 张，老图首次查询时读文件头回填），盒子按真实比例占位，**加载前后不跳版**。
- 懒加载：`IntersectionObserver` + `rootMargin: 300px`，进视口前 300px 才开始请求原图；
  无 JS 时 `<noscript>` 里的原图兜底。
- **尺寸自适应**：站内图生成 `srcSet`（240 / 360 / 480 / 720 / 960 / 1280 / 1600 七档）；
  浏览器按 `sizes` 与设备像素密度自己挑一档 —— 手机取小的，高分屏取 2x，窗口拉宽也跟着换。
  档位与 `media_variants` 的缓存键一致，同一张图每个宽度只算一次。
- 背景存 `users.profile_bg`，我的页右上角可上传 / 移除。

### 18.2 发帖编辑器

- 发帖入口是**独立悬浮弹窗**（`.composer-modal`）：背景遮罩 + 居中面板，
  点遮罩 / × / Esc 关闭，右上角可放大/还原，移动端全屏；草稿在关闭后仍保留。
- 弹窗版式：顶部「创建帖子」+ 版块/标签行 + 无边框标题 + 正文 + 底部工具栏
  （头像、格式按钮、写/预览、字数、草稿状态、舍弃/创建）。
- 版块值会作为首个标签随帖提交；标签总数最多 3 个。
- 组件 `components/markdown-editor.tsx`：工具栏（粗体 / 斜体 / 删除线 / 标题 / 引用 /
  行内代码 / 代码块 / 链接 / 列表）、写/预览切换、字数、草稿（localStorage，按昵称隔离）。
- 支持 `Ctrl+B` / `Ctrl+I` / `Ctrl+K` / `Ctrl+Enter` 发布；工具栏含表情选择器。
- 图片按钮、粘贴、拖入都会上传到 `user_media`，并插入 `![alt](/api/v1/media/…)`。
- 渲染在 `lib/markdown.tsx`，不引第三方解析器、不使用 `dangerouslySetInnerHTML`；
  原始 HTML 一律当文本，链接只放行 http(s) / 站内路径。
- 帖子详情渲染 Markdown；列表摘要用 `markdownToText()` 去标记。

### 18.3 联机大厅上传（迁移 0024）

- 上传是**右上角按钮 + 悬浮弹窗**（`.composer-modal` / `.srv-modal`），不再占右栏一整屏；
  未登录时按钮变成「登录后上传」。
- 弹窗高度**听内容**（`height: auto`，别继承发帖面板的 `88vh`，否则工具栏下面空一大截）；
  表单自己滚动、底部工具栏 `sticky` 贴底；字段区 `padding: 14px 18px`，
  页面级 `.composer-panel { padding: 0 }` 不会再把输入框顶到边线。
- ≤560px 时给 `.composer-modal:has(.srv-modal)` 补 10px 内边距，表单落成单列，
  按钮拉平占满一行（触控目标 32px+）。
- 迁移 0024 给 `game_servers` 加 `status`：`pending` / `approved` / `rejected`。
  默认 `approved` 让老数据继续展示，**新上传由应用层写 `pending`**。
- 与 `visibility` 分开：`visibility` 是「管理员暂时下架」，`status` 是「是否通过审核」。
- 公开列表与 Rusted Warfare 聚合都只取 `status='approved' AND visibility='public'`；
  探测循环同样只跑已通过的条目（省得为待审核的地址打流量）。
- `GET /api/v1/me/servers` 返回本人全部提交（含待审核 / 被拒），大厅用它渲染
  「我的提交」卡片；已通过的已经在大厅里，不重复展示。
- 后台 `PATCH /api/v1/admin/servers/{id}` 同时接受 `visibility` 与 `status`；
  待审核排在最前，通过时清空探测快照，下一轮立刻开始探。
- 同一地址唯一：若命中的是**本人被拒**的那条，重新提交会直接改回 `pending`，
  不需要先删再填；别人的地址仍返回冲突。
- 大厅首屏（参考麦块联机大厅）：标题右侧是一枚统计胶囊「N 台在线 · M 人在线 · 共 K 个」
  （绿点跟随是否有在线）；下面是「新服速递」横向小条（按 `created_at` 取 6 条，锚点直达卡片）；
  卡片按「在线 → 人数 → 新提交」排序，右栏「人气服务器」只列在线且有人数的前 3。
  统计与排序都在服务端算，客户端不再二次请求。

## 20. 缓存与限流（可选 Redis）

- `REDIS_URL` **可选**。不配时 `server/src/cache.rs` 用进程内实现：读/写带 TTL 的字符串、
  固定窗口计数，接口行为完全一致；配了就连 Redis，多实例之间才共享。
- 连不上不会阻止启动，只打一条 warn 并降级——自托管常见「配了但容器还没起来」。
- 目前用在哪：
  | 位置 | 键 | 窗口 / TTL |
  |---|---|---|
  | 登录 | `rl:login:{用户名}` | 10 次 / 分钟，**成功即清零** |
  | 私信发送 | `rl:dm:{用户 id}` | 30 条 / 分钟 |
  | 公开统计 | `cache:public:stats` | 30 秒 |
- compose 里 **redis 默认随栈启动**（`docker compose up -d` 就会拉起），
  并作为 api 的 `depends_on` 健康依赖；`REDIS_URL` 缺省为 `redis://redis:6379/0`。
- 不想用 Redis：`docker compose up -d db api`，或把 `REDIS_URL` 显式设成空字符串。
- 多实例部署**必须**用 Redis（默认已开），否则每台的限流各算各的。

## 21. 任务中心

- 迁移 0026：`tasks`（规则）+ `task_claims`（领取记录，`(user, task, period_key)` 主键）。
- 进度**不落计数器**：按当期起点实时统计 `checkins / posts / comments / likes / resources /
  game_servers`。日 / 周按上海时区切，一次性任务从 epoch 起算。
- `GET /api/v1/tasks` 返回任务定义 + `progress / claimed / claimable / periodKey`；
  `POST /api/v1/tasks/{id}/claim` 先校验进度，再靠唯一键防重复领取，最后走 `points::award`
  （`reason='task'`）。后台 `GET/POST/PATCH/DELETE /api/v1/admin/tasks`。
- 前台 `/tasks`：按每日 / 每周 / 一次性分组，进度条 + 领取；后台 `/admin/tasks`
  定义周期、指标、目标次数与奖励积分。

## 22. 赛事

- 迁移 0027：`tournaments` + `tournament_entries`。与「约战」分开：约战是两队私下约时间，
  赛事是官方活动，有报名窗口、名额与赛程。
- 状态：`draft → signup → running → ended`。`draft` 只有管理员能读；报名只在 `signup`
  且处于窗口内开放，名额按 `pending + approved` 计算，满了拒绝。
- 报名唯一键 `(tournament_id, user_id)`；被拒的可以改资料重新提交（复用同一条记录）。
- 接口：`GET /api/v1/tournaments`、`GET /{id}`（含 `entries` 与我的报名）、
  `POST /{id}/signup`、`DELETE /{id}/signup`；后台 CRUD 与
  `PATCH /api/v1/admin/tournaments/entries/{entryId}` 审核报名。
- 前台 `/tournaments`（报名中 / 进行中 + 已结束）、`/tournaments/[id]`（赛程、奖品、队伍、报名）；
  后台 `/admin/tournaments` 创建编辑、报名审核。
- 主办方（迁移 0028）：`host_user_id` 记创建赛事的后台账号，`host_name` 是对外显示名
  （空则回落到站点名）。证书判定只看 `host_user_id`，所以「主办证书」发给真正办赛的账号。
- 证书（`/tournaments/[id]/certificate`）：主办证书 + 参赛证书，同一页两枚页签；
  参赛证书要求报名 `approved`。Canvas 画 1600×1131（A4 横向），页面上看到的就是导出图，
  编号用 `certSerial('TN-xxxx', holder)` 生成，同一人每次一致。
- 宣传图：详情页右栏「分享与宣传」用 `renderTournamentPoster` 生成 1080×1350 竖版海报
  （主视觉、赛程、名额、奖品、站内地址）。封面只读站内路径，跨域图会污染画布导致导不出 PNG。
